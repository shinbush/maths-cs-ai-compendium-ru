# Масштабирование и развертывание

*Для обслуживания больших моделей миллионам пользователей необходимо распределять логические выводы между несколькими графическими процессорами, прогнозировать токены до того, как они потребуются, кэшировать общий контекст и выбирать правильную платформу. В этом файле описаны параллелизм при выводе, спекулятивное декодирование, кэширование префиксов, платформы вывода, оптимизация затрат и мониторинг.*

- Один графический процессор H100, обслуживающий модель 70B, может обслуживать около 100 одновременных пользователей с интерактивной задержкой. Для обслуживания 10 миллионов пользователей требуется 100 000 графических процессоров, что обходится примерно в 3 миллиарда долларов в год на облачные вычисления. Каждый процент повышения эффективности экономит десятки миллионов долларов. Вот почему оптимизация вывода не является академической: она напрямую определяет экономику продуктов ИИ.

## Модельный параллелизм при выводе

- Если модель слишком велика для одного графического процессора, ее необходимо разделить на несколько графических процессоров. Стратегии параллелизма из обучения (глава 6) применяются при выводе с различными компромиссами.

### Тензорный параллелизм

- **Тензорный параллелизм** (в стиле Мегатрона, глава 6) разделяет отдельные весовые матрицы между графическими процессорами. Для линейного слоя $Y = XW$ весовая матрица $W$ разбивается по столбцам между графическими процессорами $N$. Каждый графический процессор вычисляет частичный результат, а затем суммирует все значения:

$$W = [W_1 | W_2 | \cdots | W_N], \quad Y_i = X W_i, \quad Y = \text{concat}(Y_1, \ldots, Y_N)$$

- При выводе тензорный параллелизм используется по умолчанию для моделей, которые не помещаются на один графический процессор. Для модели 70B в FP16 требуется 140 ГБ, разделенных на 2 графических процессора по 80 ГБ с тензорным параллелизмом.

- **Влияние задержки**: тензорный параллелизм добавляет полностью сокращенный шаг связи на каждом уровне. На NVLink (900 ГБ/с) это добавляет ~0,1 мс на уровень. На PCIe (32 ГБ/с) это добавляет ~3 мс на каждый уровень. Для модели 70B с 80 слоями на 2 графических процессорах: NVLink добавляет всего ~8 мс, PCIe — ~240 мс. Вот почему NVLink имеет огромное значение для вывода данных с использованием нескольких графических процессоров.

### Параллелизм конвейеров

- **Конвейерный параллелизм** назначает разные уровни разным графическим процессорам. Графический процессор 1 обрабатывает слои 0–39, графический процессор 2 обрабатывает слои 40–79. Токены проходят через конвейер последовательно.

- При выводе конвейерный параллелизм имеет более высокую задержку, чем тензорный параллелизм (для каждого токена необходимо пройти весь конвейер), но меньшие накладные расходы на связь (между графическими процессорами передаются только активации, без полного сокращения). Предпочтительно, когда графические процессоры соединены медленными межсоединениями (разные узлы, без NVLink).

### Параллелизм последовательностей

— Для очень длинных последовательностей сам KV-кэш может не поместиться на один графический процессор, даже если модель подходит. **Параллелизм последовательностей** распределяет KV-кэш между графическими процессорами: каждый графический процессор хранит часть кэшированных ключей и значений последовательности.

- Во время внимания каждый графический процессор вычисляет частичные оценки внимания для своего кэшированного сегмента, затем сокращение объединяет результаты. Это используется при выводе длинного контекста (более 128 000 токенов), когда KV-кэш превышает объем памяти одного графического процессора.

## Спекулятивное декодирование

- **Спекулятивное декодирование** — одна из наиболее эффективных оптимизаций вывода LLM. Вывод: декодирование происходит медленно, поскольку оно генерирует по одному токену за раз, причем каждый токен требует полного прямого прохода большой модели. Но маленькая модель может генерировать токены-кандидаты гораздо быстрее, а большая модель может **проверять** несколько кандидатов параллельно.

![Speculative decoding: a fast draft model generates 5 candidate tokens, the target model verifies all in one pass, accepted tokens are kept and rejected ones resampled](../images/speculative_decoding.svg)

- **Алгоритм**:
    1. **Черновая модель** (маленькая, быстрая — например, параметры 1B) генерирует токены-кандидаты $k$ авторегрессионно.
    2. **целевая модель** (большая и точная — например, 70B) выполняет один прямой проход по всей черновой последовательности, вычисляя вероятность каждого токена-кандидата.
    3. Каждый кандидат считается **принятым**, если целевая модель согласуется (ее вероятность для этого токена достаточно высока). Отклоненные кандидаты повторно выбираются из распределения целевой модели.
    4. В среднем за один этап проверки принимается несколько токенов, что дает ускорение, пропорциональное скорости принятия.

$$\text{Speedup} \approx \frac{k \times \text{acceptance\_rate}}{\text{cost\_ratio}} \approx 2\text{-}3\times$$

- **Почему это работает без потери качества**: схема отбраковочной выборки гарантирует, что выходное распределение точно соответствует целевой модели. Спекулятивное декодирование осуществляется без потерь — результат статистически идентичен запуску только целевой модели, только быстрее.- **Варианты**:
    - **Медуза** (Cai et al., 2024): вместо отдельной черновой модели добавьте в целевую модель несколько облегченных «голов», которые одновременно прогнозируют несколько будущих токенов. Никакой отдельной модели не требуется.
    - **EAGLE** (Li et al., 2024): обучает облегченную черновую голову, которая использует скрытые состояния целевой модели для прогнозирования будущих токенов. Более высокий уровень принятия, чем независимые черновые модели.
    - **Самоспекулятивное декодирование**: целевая модель сама создает черновики, используя ранний выход (запустите только первые несколько слоев черновика, затем сверьтесь с полной моделью).
    - **Параллельное декодирование**: параллельно генерируйте несколько продолжений (дерево кандидатов) и проверяйте все дерево сразу. Более высокая пропускная способность, но используется больше памяти для ветвящихся KV-кэшей.

## Кэширование префиксов

- Многие запросы имеют общие префиксы: системные подсказки, примеры или общие шаблоны запросов. **Кэширование префиксов** сохраняет KV-кэш для этих префиксов и повторно использует его при выполнении запросов.

- **Кэширование системных приглашений**: если каждый запрос начинается с одного и того же системного приглашения из 2000 токенов, KV-кэш для этих 2000 токенов вычисляется один раз и используется всеми запросами. Для модели 70B с 80 слоями это экономит ~200 МБ на запрос.

- **Кэширование поразрядного дерева** (SGLang): организация кэшированных префиксов в поразрядном дереве (trie). Когда поступает новый запрос, найдите самое длинное совпадение кэшированного префикса и начните генерацию оттуда, пропуская вычисление соответствующего префикса.

- **Воздействие**: для приложений с длинными общими префиксами (чат-боты с системными подсказками, RAG с общими извлеченными фрагментами) кэширование префиксов снижает TTFT на 50–90 % и экономит пропорциональные вычисления на графическом процессоре.

## Удаление KV-кеша

- Помимо квантования KV-кэша (файл 01) и использования GQA/MLA для уменьшения его размера (файл 02), политики **вытеснения KV-кэша** выборочно удаляют кэшированные токены, которые вряд ли будут использоваться в будущем.

- **H2O** (Heavy-Hitter Oracle, Zhang et al., 2023) отмечает, что показатели внимания подчиняются степенному закону: небольшая часть токенов («сильные нападающие») получает большую часть внимания, в то время как большинству уделяется незначительное внимание. H2O сохраняет:

    1. **Последние токены** (скользящее окно последних токенов $w$, например StreamingLLM).
    2. **Токены с сильным нападающим** (токены $k$ с наибольшим количеством очков внимания на всех прошлых этапах декодирования).

- Токены, которые не являются ни недавними, ни активными, удаляются. Это поддерживает KV-кэш фиксированного размера, сохраняя при этом токены, которые действительно влияют на генерацию. H2O достигает качества, близкого к полному KV-кэшу, используя всего 20% памяти.

- **Руки-ножницы** (Лю и др., 2023) использует аналогичный подход, но использует более сложную метрику важности: токены, которым уделяется повышенное внимание на **текущем** этапе, сохраняются, а токены, которые не были обработаны на шагах $T$, вытесняются. Это адаптируется к изменению структуры внимания во время генерации.

- **Динамическое вытеснение + StreamingLLM**: комбинируйте приемники внимания (постоянно сохраняйте первые несколько токенов) с динамическим вытеснением (сохраняйте последние + наиболее важные токены). Это наиболее эффективный подход к использованию памяти для очень длинной генерации, позволяющий генерировать бесконечную длину с ограниченным ухудшением качества.

- Ключевая идея всех методов вытеснения: внимание LLM **на практике редко** — даже несмотря на то, что архитектура вычисляет внимание по всем кэшированным токенам, фактические веса внимания концентрируются на небольшом подмножестве. Удаление остальных оказывает минимальное влияние на качество вывода.

– **vLLM** — выбор по умолчанию для обслуживания производственного LLM. Он поддерживает непрерывную пакетную обработку, PagedAttention, тензорный параллелизм, спекулятивное декодирование, обслуживание LoRA и большинство моделей с открытым исходным кодом.

- **TensorRT-LLM** обеспечивает высочайшую производительность на оборудовании NVIDIA (на 10–30 % быстрее, чем vLLM на том же графическом процессоре), но он менее гибок и его сложнее настроить.

- **SGLang** превосходно работает, когда приложения имеют структурированный вывод (JSON, код определенного формата) или общие префиксы, благодаря своему поразрядному кэшу внимания и механизму ограниченного декодирования.

## Оптимизация затрат

- В масштабе стоимость вывода доминирует в бюджетах ML. Стратегии снижения затрат:

- **Правильный выбор графического процессора**: не каждой модели нужен H100. Квантованная модель 7B хорошо работает на A10G (~$1/hr) instead of an H100 (~$8/час). Сопоставьте графический процессор с рабочей нагрузкой.

- **Спотовые инстансы**: поставщики облачных услуг предлагают неиспользуемую мощность графического процессора со скидкой 60–90 % (спотовые инстансы AWS, вытесняемые GCP). Спотовые инстансы могут быть прерваны, поэтому они работают для пакетного вывода, но не для обслуживания с критическим значением задержки. В сочетании с опережающей обработкой (сохранение состояния, возобновление работы на новом экземпляре) спотовые экземпляры также могут обслуживать интерактивный трафик.

- **Автомасштабирование**: масштабируйте количество графических процессоров в зависимости от трафика. Увеличивайте масштаб в часы пик и уменьшайте ночью. С этой задачей справляются Kubernetes HPA (Horizontal Pod Autoscaler) или облачное автомасштабирование (AWS SageMaker, GCP Vertex AI).

- **Пакетирование + использование**: разница между 30% и 90% использованием графического процессора в 3 раза увеличивает стоимость токена. Непрерывная пакетная обработка, интеллектуальное планирование и PagedAttention повышают эффективность использования.

- **Квантование**: INT4 по сравнению с FP16 требует в 4 раза меньше памяти → подходит для меньшего графического процессора → в 2–4 раза дешевле. Кроме того, в один пакет помещается больше запросов → более высокая пропускная способность → более низкая стоимость токена.

- **Цена за токен** (приблизительно, 2026 г.):

| Настройка | Стоимость за 1 миллион токенов |
|-------|-------------------|
| API GPT-4o | 2,50 доллара США |
| Клод 3.5 Сонет API | $3,00 |
| Лама-70Б на H100 (vLLM, FP16) | 0,50 доллара США |

| Лама-3B на устройстве (llama.cpp) | $0 (оборудование амортизировано) |

## Мониторинг

- Производственный вывод требует постоянного мониторинга для выявления деградации до того, как она повлияет на пользователей:

- **Мониторинг задержки**: отслеживайте TTFT и TPOT на точках p50, p95 и p99. Установите оповещения о превышении SLO p99. Пик p99 часто указывает на: нехватку памяти KV-кэша (перегрузка), длительный запрос, монополизирующий пакет, или тепловое регулирование графического процессора.

- **Мониторинг пропускной способности**: отслеживайте количество токенов в секунду на каждый графический процессор. Снижение указывает на снижение эффективности пакетов (много коротких запросов → низкое использование пакетов), увеличение длины последовательности (больше KV-кэш-памяти на запрос) или аппаратные проблемы (графический процессор в режиме исправления ошибок ECC, работает медленнее).

- **Использование графического процессора**: отслеживание занятости SM, использования памяти и пропускной способности памяти. Низкая занятость SM + высокая загрузка памяти = ограничена памятью (требуется большая полоса пропускания или квантование). Высокая занятость SM + низкое использование памяти = ограничено вычислительными ресурсами (нужно больше FLOPS или меньшая модель).- **Мониторинг качества модели**: отслеживайте показатели каждого запроса (длина ответа, недоумение в заданном наборе, сигналы обратной связи с пользователем). Качество модели может ухудшиться из-за: дрейфа данных (изменения распределения входящих запросов), ошибок квантования KV-кэша, накапливающихся в ходе длительных диалогов, или ошибок в обслуживающем конвейере.

- **Мониторинг затрат**: отслеживайте стоимость токена, модели и типа графического процессора. Если стоимость увеличивается без увеличения пропускной способности, исследуйте снижение эффективности (новая версия модели с более высоким использованием памяти, неоптимальная пакетная конфигурация или недостаточно загруженные графические процессоры).

- **Инструменты**: Prometheus + Grafana (глава 15) для метрик инфраструктуры, встроенные конечные точки метрик vLLM/TRT-LLM и настраиваемое ведение журналов для метрик на уровне модели.

## Задачи по кодированию (используйте CoLab или блокнот)

1. Имитировать спекулятивное декодирование. Используйте быструю «черновую» функцию и медленную «целевую» функцию и измерьте ускорение при одновременной генерации и проверке нескольких токенов.
```python
import random
import time

def target_model(tokens):
    """Slow but accurate model. Returns probability of each candidate token."""
    time.sleep(0.01)  # simulate 10ms per forward pass
    # For simulation: accept tokens that are even numbers
    return [0.9 if t % 2 == 0 else 0.1 for t in tokens]

def draft_model():
    """Fast but approximate model. Generates one candidate token."""
    time.sleep(0.001)  # simulate 1ms per token
    return random.randint(0, 9)

def standard_decoding(n_tokens):
    """Generate one token at a time with the target model."""
    tokens = []
    for _ in range(n_tokens):
        time.sleep(0.01)  # target model generates 1 token
        tokens.append(random.randint(0, 9))
    return tokens

def speculative_decoding(n_tokens, k=4):
    """Generate k draft tokens, verify with target, accept/reject."""
    tokens = []
    total_target_calls = 0

    while len(tokens) < n_tokens:
        # Draft: generate k candidates quickly
        candidates = [draft_model() for _ in range(k)]

        # Verify: one target model call for all k candidates
        probs = target_model(candidates)
        total_target_calls += 1

        # Accept tokens until one is rejected
        for i, (tok, prob) in enumerate(zip(candidates, probs)):
            if random.random() < prob:
                tokens.append(tok)
                if len(tokens) >= n_tokens:
                    break
            else:
                # Resample from target distribution
                tokens.append(tok + 1)  # simplified resampling
                break

    return tokens, total_target_calls

n = 50

start = time.time()
_ = standard_decoding(n)
standard_time = time.time() - start

start = time.time()
_, target_calls = speculative_decoding(n, k=5)
```

```python
def serving_cost_analysis(
    model_name, params_B, precision_bits,
    gpu_name, gpu_mem_gb, gpu_cost_per_hr,
    target_throughput_tps,
):
    """Estimate serving cost for an LLM deployment."""
    model_size_gb = params_B * 1e9 * precision_bits / 8 / 1e9
    gpus_for_model = max(1, int((model_size_gb * 1.2) / gpu_mem_gb + 0.99))  # 1.2x for KV-cache

    # Rough throughput estimate (memory-bandwidth limited)
    tokens_per_gpu = 500 / (params_B * precision_bits / 16)  # normalised to 500 tok/s for 7B FP16
    total_throughput = tokens_per_gpu * gpus_for_model

    replicas = max(1, int(target_throughput_tps / total_throughput + 0.99))
    total_gpus = gpus_for_model * replicas
    cost_per_hr = total_gpus * gpu_cost_per_hr
    cost_per_1M_tokens = cost_per_hr / (total_throughput * replicas * 3600 / 1e6)

    print(f"{model_name} @ {precision_bits}-bit on {gpu_name}:")
    print(f"  Model size: {model_size_gb:.0f} GB → {gpus_for_model} GPU(s)/replica")
    print(f"  Throughput: {total_throughput:.0f} tok/s/replica")
    print(f"  Replicas for {target_throughput_tps} tok/s: {replicas}")
    print(f"  Total GPUs: {total_gpus}")
    print(f"  Cost: ${cost_per_hr:.0f}/hr, ${cost_per_1M_tokens:.2f}/1M tokens")
    print()

print("=== Cost Comparison ===\n")

# Baseline: FP16 on H100
serving_cost_analysis("Llama-70B", 70, 16, "H100", 80, 8.0, 1000)
```
