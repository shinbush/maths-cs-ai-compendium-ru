# Облачные вычисления

*Облачные вычисления обеспечивают инфраструктуру по требованию для рабочих нагрузок машинного обучения без владения оборудованием. В этом файле описаны модели сервисов, основные поставщики облачных услуг, контейнеры и Kubernetes, хранилища, облачные сети, бессерверные вычисления, управление затратами и инфраструктура в виде кода*.

— Обучение пограничной модели требует использования тысяч графических процессоров в течение нескольких месяцев. Ни один стартап не владеет таким оборудованием. Облачные вычисления позволяют арендовать их почасово, масштабировать для обучения, уменьшать для логических выводов и платить только за то, что вы используете. Понимание облачной инфраструктуры необходимо для любого, кто создает системы машинного обучения за пределами ноутбука.

## Модели облачных сервисов

![Cloud service layers: IaaS gives you most control, SaaS gives you least](../images/cloud_service_layers.svg)

- Облачные услуги разделены по уровням в зависимости от того, насколько управляет провайдер:

| Модель | Вы управляете | Провайдер управляет | Пример |
|-------|-----------|-----------------|---------|
| **IaaS** (Инфраструктура) | ОС, среда выполнения, приложение | Аппаратное обеспечение, виртуализация, сети | AWS EC2, вычислительная система GCP |
| **PaaS** (Платформа) | Приложение, данные | ОС, среда выполнения, масштабирование, исправление | AWS SageMaker, GCP Vertex AI |
| **SaaS** (Программное обеспечение) | Ничего (просто используйте) | Всё | OpenAI API, веса и смещения |
| **FaaS** (Функция) | Отдельные функции | Все остальное | AWS Lambda, облачные функции GCP |

– **Для ML**: большинство команд используют смешанный вариант. IaaS для индивидуального обучения (полный контроль над экземплярами графического процессора), PaaS для управляемого обучения и обслуживания (SageMaker, Vertex AI обеспечивает оркестрацию) и SaaS для инструментов (W&B для отслеживания экспериментов, OpenAI API для базового сравнения).

## Крупнейшие провайдеры

### AWS (Веб-сервисы Amazon)

- Крупнейший облачный провайдер (~32% рынка). Ключевые услуги ОД:
    - **EC2**: виртуальные машины. Экземпляры графического процессора: p4d (A100), p5 (H100), g5 (A10G для вывода).
    - **S3**: хранилище объектов. Стандарт хранения наборов данных и весов моделей. Практически неограниченная емкость, ~0,023 доллара США/ГБ/месяц.
    - **SageMaker**: управляемая платформа машинного обучения. Обеспечивает обучение, настройку гиперпараметров, развертывание и мониторинг.
    - **EKS**: управление Kubernetes.
    - **Лямбда**: бессерверные функции. Не подходит для рабочих нагрузок графического процессора, но полезен для предварительной обработки и оркестровки.

### GCP (Облачная платформа Google)

- Облако Google (~11% рынка). Ключевые услуги ОД:
    - **Compute Engine**: виртуальные машины. Экземпляры графического процессора с A100, H100. **Виртуальные машины TPU** для доступа к TPU.
    - **GCS**: хранилище объектов (например, S3).
    - **Vertex AI**: управляемая платформа машинного обучения. Встроенная поддержка JAX/TPU.
    - **GKE**: управляемый Kubernetes (наиболее зрелое предложение K8 с тех пор, как Google создал Kubernetes).
    - **Облачные TPU**: эксклюзивно для GCP. v5e и v5p для масштабного обучения.

### Azure (Майкрософт)

- Облако Microsoft (~23% рынка). Ключевые услуги ОД:
    - **Виртуальные машины Azure**: экземпляры графического процессора с A100, H100.
    - **Хранилище BLOB-объектов Azure**: хранилище объектов.
    - **Azure ML**: управляемая платформа машинного обучения.
    - **AKS**: управление Kubernetes.
    - **Сервис OpenAI**: эксклюзивный доступ к моделям OpenAI через API Azure.

## Контейнеры и Kubernetes

- Мы рассмотрели контейнеры (Docker) и Kubernetes концептуально в главе 13 (ОС) и практически в главе 15 (развертывание). Здесь мы сосредоточимся на **специфичных для облака** шаблонах:

### Kubernetes для машинного обучения

- **Kubernetes (K8s)** организует контейнеры в любом масштабе. Ключевые понятия:

    - **Под**: наименьшая развертываемая единица. Содержит один или несколько контейнеров, совместно использующих сеть и хранилище. Модуль обслуживания модели может содержать: контейнер сервера модели + дополнительный контейнер для сбора метрик.

    - **Развертывание**: управляет набором идентичных модулей. Указывает желаемое количество реплик. Если модуль выйдет из строя, K8s автоматически создаст замену.

    - **Сервис**: стабильная конечная точка сети для набора модулей. Клиенты подключаются к сервису; K8s направляется в исправный модуль. Типы: ClusterIP (внутренний), NodePort (внешний через порт узла), LoadBalancer (внешний через облачный LB).

    - **StatefulSet**: аналогично развертыванию, но для рабочих нагрузок с отслеживанием состояния. Каждый модуль получает постоянную идентификацию и стабильное хранилище. Используется для баз данных и распределенного обучения (каждому работнику для общения требуется стабильная личность).- **DaemonSet**: запускает один модуль на каждом узле. Используется для: агентов мониторинга (экспортер узлов Prometheus), сборщиков журналов (Fluentd), плагинов устройств графического процессора (плагин устройств NVIDIA).

- **Планирование графического процессора в K8s**: плагин устройства NVIDIA предоставляет графические процессоры как ресурс K8s. Поды запрашивают графические процессоры:

```yaml
resources:
  limits:
    nvidia.com/gpu: 2  # this pod needs 2 GPUs
```

- K8s планирует модуль на узле с двумя доступными графическими процессорами. Именно так платформы облачного машинного обучения выделяют графические процессоры для обучения и вывода.

### Автомасштабирование

- **Горизонтальное автомасштабирование модулей (HPA)**: масштабирует количество модулей на основе показателей (загрузка ЦП, частота запросов, пользовательские показатели, такие как загрузка графического процессора или глубина очереди).

- **Автомасштабирование кластера**: масштабирует количество узлов. Если модули не могут быть запланированы из-за недостаточного количества узлов, автомасштабирование кластера предоставляет новые виртуальные машины от поставщика облака. Когда узлы используются недостаточно, они истощаются и отключаются.

- **KEDA** (автомасштабирование на основе событий Kubernetes): масштабируется на основе внешних источников событий (глубина очереди Kafka, частота HTTP-запросов). Идеально подходит для вывода: масштабируйте серверы моделей, когда очередь запросов растет, и уменьшайте масштаб, когда она пуста.

## Хранилище

| Тип | Характеристики | Вариант использования | Пример |
|------|----------------|----------|---------|
| **Блокировать** | Низкая задержка, подключение к одной виртуальной машине | Диски ОС, базы данных | AWS EBS, постоянный диск GCP |
| **Объект** | Неограниченная емкость, доступ по HTTP | Наборы данных, веса моделей, журналы | AWS S3, GCS, Azure Blob |
| **Файл** | Совместно используется всеми виртуальными машинами, POSIX | Общие данные обучения | AWS EFS, хранилище файлов GCP, NFS |
| **Озеро данных** | Чтение схемы, необработанные данные | Аналитика, разработка функций | Озеро Дельта, Айсберг, Худи |

- **Для обучения машинному обучению**: наборы данных хранятся в объектном хранилище (S3/GCS). Скрипты обучения считывают данные из объектного хранилища в оперативную память. Для быстрого произвольного доступа (загрузка данных в случайном порядке): (1) загрузите набор данных на локальный твердотельный накопитель перед обучением, (2) используйте файловую систему с высокой пропускной способностью (Lustre, FSx) или (3) используйте библиотеку загрузки данных, которая эффективно выполняет потоковую передачу и кэширование (WebDataset, FFCV).

- **Вес модели**: хранится в хранилище объектов с контролем версий. Модель 70B в FP16 занимает ~140 ГБ. Загрузка с S3 на скорости 1 ГБ/с занимает ~2,5 минуты. Кэширование на локальном SSD сокращает время холодного запуска для вывода.

## Облачная сеть

- **VPC** (виртуальное частное облако): изолированная сеть внутри облака. Ваши виртуальные машины, базы данных и сервисы взаимодействуют внутри VPC. Внешний трафик поступает через балансировщики нагрузки или шлюзы.

- **Подсети**: разделите VPC на сегменты. Публичные подсети имеют доступ в Интернет (для серверов API). Частных подсетей нет (для баз данных и работников графического процессора). Это сетевой эквивалент принципа безопасности наименьших привилегий.

- **Группы безопасности** (AWS) / **Правила брандмауэра** (GCP): контролируйте, какой трафик разрешен. «Разрешить входящий HTTP на порт 80 откуда угодно. Разрешить входящий SSH на порт 22 только с моего IP. Заблокировать все остальное». Неправильно настроенные группы безопасности являются основной причиной инцидентов безопасности в облаке.

- **Сервисная сетка** (Istio, Envoy): управляет связью между сервисами внутри K8s. Обеспечивает: шифрование mTLS (каждый межсервисный вызов шифруется), маршрутизацию трафика (A/B-тестирование: перенаправляет 10 % трафика на новую модель), повторные попытки, таймауты, разрыв цепи и наблюдаемость (какая служба какую вызывала, сколько времени это заняло).

## Бессерверный

- **Бессерверная** (AWS Lambda, облачные функции GCP): вы загружаете функцию, и поставщик облака запускает ее при запуске. Никаких серверов, которыми нужно управлять, и никакого масштабирования, требующего настройки. Вы платите за каждый вызов (обычно 0,20 доллара США за 1 миллион вызовов + время вычислений).

- **Холодный старт**: первый вызов после периода бездействия занимает больше времени (провайдер должен выделить контейнер и загрузить ваш код). Холодный запуск занимает 0,5–5 секунд, что делает бессерверные решения непригодными для вывода машинного обучения, чувствительного к задержке.

- **Для машинного обучения**: бессерверное использование полезно для: предварительной обработки (изменение размера изображений перед отправкой в ​​модель), постобработки (форматирование выходных данных модели, отправка уведомлений), оркестрации (запуск конвейера обучения при поступлении новых данных) и упрощенного вывода (небольшие модели с устойчивостью к холодному запуску).- Бессерверная технология **не** подходит для: вывода графического процессора (без поддержки графического процессора на большинстве бессерверных платформ), длительных учебных заданий (15-минутный тайм-аут в Lambda) или служб с отслеживанием состояния (нет постоянного состояния между вызовами).

## Управление затратами

— Затраты на облако — это операционная проблема номер один для команд ML. Стоимость одного экземпляра H100 составляет ~$8/hour. A 64-GPU training run costs ~$500 в час. Месячное обучение стоит около 360 000 долларов. Оптимизация затрат – это инженерия, а не учет.

- **Спотовые/вытесняемые инстансы**: неиспользуемые облачные ресурсы продаются со скидкой 60–90 %. Поставщик может вернуть их с уведомлением за 30 секунд до 2 минут. Использование для: отказоустойчивого обучения (частая проверка, возобновление работы на новых экземплярах), пакетного вывода, предварительной обработки данных. Не для: обслуживания, чувствительного к задержке (прерывание = время простоя).

- **Зарезервированные экземпляры**: используйте 1–3 года со скидкой 30–60 %. Используется для: вывода установившегося состояния, когда вы знаете базовую нагрузку.

- **Автомасштабирование**: увеличение в часы пик, уменьшение ночью или в выходные дни. Модельный сервер, которому требуется 10 графических процессоров в пиковую нагрузку и 2 в ночное время, экономит около 60 % за счет автоматического масштабирования по сравнению с работой 10 графических процессоров в режиме 24/7.

- **Правильный размер**: не используйте H100 для модели 7B, которая отлично работает на A10G. Сопоставьте графический процессор с рабочей нагрузкой. Используйте профилирование (глава 16), чтобы определить, какой графический процессор подходит лучше всего.

- **Затраты на хранение**: хранилище объектов обходится дешево ($0.023/GB/month for S3 Standard), but accumulates. A team storing every training checkpoint (10 GB each, 100 per experiment, 50 experiments) accumulates 50 TB = $1,150 в месяц). Установите политики жизненного цикла для автоматического удаления старых контрольных точек.

## Развертывание в нескольких регионах

- Для глобальных систем машинного обучения (обслуживающих пользователей по всему миру) развертывание в одном регионе означает высокую задержку для удаленных пользователей (пользователь в Токио, обращающийся к американскому серверу, добавляет около 150 мс к сети туда и обратно) и единственную точку отказа (если регион выходит из строя, вся служба отключается).

- **Мультирегиональные шаблоны**:

    - **Активный-пассивный**: весь трафик обрабатывается одним основным регионом. Дополнительный регион имеет «теплый» резерв (реплицированные данные, готовые к приему трафика). При первичном сбое DNS переключается на вторичный. Время простоя при аварийном переключении: от 30 секунд до нескольких минут.

    - **Активный-активный**: оба региона обрабатывают трафик одновременно. Пользователи перенаправляются в ближайший регион. Оба региона имеют актуальные данные (реплицируются асинхронно или синхронно). Никаких простоев при сбое в одном регионе — трафик перенаправляется автоматически.

- **Репликация данных**: самое сложное. Веса моделей можно легко воспроизвести (скопировать в S3 в каждом регионе). Данные хранилища функций должны реплицироваться с приемлемой степенью устаревания. Пользовательские данные могут иметь **требования к местонахождению данных** (GDPR: европейские пользовательские данные должны оставаться в Европе).

- **Сравнение цен на облачные процессоры** (приблизительно, 2026 г.):

| графический процессор | АВС | GCP | Лазурный | Типичное использование |
|-----|-----|-----|-------|-------------|
| А10Г (24 ГБ) | $1.00/hr (g5) | $0,90/час | 0,90 доллара США в час | Небольшой вывод модели |
| А100 (80 ГБ) | $4.10/hr (p4d) | $3,70/час | 3,40 доллара в час | Обучение, большой вывод |
| H100 (80 ГБ) | $8.00/hr (p5) | $7,50/час | $7,00/час | Пограничное обучение |

- Спотовые/преимущественные цены обычно на 60–70 % ниже этих ставок. Цены варьируются в зависимости от региона и наличия.

## Инфраструктура как код

- **IaC** определяет инфраструктуру (виртуальные машины, сети, базы данных, кластеры K8s) в файлах конфигурации с контролем версий. Вместо того, чтобы нажимать кнопки в консоли AWS, вы пишете код, описывающий то, что вы хотите, а инструмент создает это.

- **Terraform** (HashiCorp): стандартный инструмент IaC. Работает со всеми основными облачными провайдерами. Декларативный: вы описываете желаемое состояние, Terraform определяет, что нужно создать/изменить/удалить, чтобы его достичь.

```hcl
# main.tf — create a GPU VM for inference
resource "aws_instance" "model_server" {
  ami           = "ami-0abcdef1234567890"  # Deep Learning AMI
  instance_type = "g5.xlarge"               # A10G GPU

  tags = {
    Name = "model-server-prod"
  }
}

resource "aws_s3_bucket" "model_weights" {
  bucket = "my-model-weights-prod"

  versioning {
    enabled = true
  }
}
```

```bash
terraform init      # download provider plugins
terraform plan      # show what will change
terraform apply     # create the infrastructure
terraform destroy   # tear it all down
```

- **Почему IaC имеет значение**: воспроизводимость (воссоздание всей инфраструктуры из кода), аудит (история git показывает, кто что изменил), аварийное восстановление (перестроение в другом регионе из той же конфигурации) и четность среды (разработчики, промежуточные и производственные версии используют одни и те же шаблоны с разными параметрами).

- **Pulumi**: похож на Terraform, но использует настоящие языки программирования (Python, TypeScript, Go) вместо HCL. Полезно, когда логика вашей инфраструктуры сложна (условия, циклы, динамическая конфигурация).
