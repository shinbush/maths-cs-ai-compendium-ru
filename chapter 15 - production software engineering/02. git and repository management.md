# Git и контроль версий

*Git — это то, как команды разработчиков сотрудничают, не перезаписывая работу друг друга. В этом файле описывается ментальная модель Git, стратегии ветвления, слияние и перебазирование, разрешение конфликтов, запросы на включение и управление специфическими проблемами машинного обучения, такими как большие файлы и отслеживание экспериментов.*

— В каждом серьезном программном проекте используется контроль версий. **Git** — доминирующая система, используемая практически всеми проектами и компаниями с открытым исходным кодом. Без git совместная работа — это отправка zip-файлов по электронной почте и молитва, чтобы никто не перезаписал ваши изменения. С помощью git каждое изменение отслеживается, обратимо и может быть атрибутировано.

- Для инженеров ML: git отслеживает ваш код, конфигурации и сценарии экспериментов. В сочетании с инструментами отслеживания экспериментов это дает вам воспроизводимость: «какой именно код и конфигурация создали эту модель?»

## Ментальная модель

- Git отслеживает **снимки** вашего проекта. Каждый коммит представляет собой полный снимок всех отслеживаемых файлов на данный момент, а не разницу (внутри git хранит различия для повышения эффективности, но концептуально каждый коммит представляет собой полное состояние).

- Четыре «места» для ваших файлов:

    1. **Рабочий каталог**: файлы на диске. Вы редактируете их.
    2. **Область подготовки** (индекс): файлы, которые вы пометили для следующего коммита. `git add` перемещает изменения сюда.
    3. **Локальный репозиторий**: ваша история коммитов, хранящаяся в `.git/`. `git commit` сохраняет промежуточную область как новый снимок.
    4. **Удаленный репозиторий** (например, GitHub): общая копия. `git push` загружает ваши коммиты, `git pull` загружает чужие.

```
Working Dir  →  git add  →  Staging  →  git commit  →  Local Repo  →  git push  →  Remote
                                                        ←  git pull  ←
```

— Промежуточная область — это то, что делает git мощным. Вы можете редактировать 10 файлов, но зафиксировать только 3 из них, оставив остальные изменения для отдельной фиксации. Это обеспечивает чистые, целенаправленные коммиты.

### Основные команды

```bash
git init                          # create a new repository
git clone url                     # download a remote repository
git status                        # what has changed? (most-used command)
git add file.py                   # stage a specific file
git add .                         # stage all changes (use with caution)
git commit -m "descriptive msg"   # commit staged changes
git push                          # upload commits to remote
git pull                          # download + merge remote changes
git log --oneline                 # compact commit history
git diff                          # show unstaged changes
git diff --staged                 # show staged changes
```

## Ветвление

- **ветвь** — это указатель на коммит. Ветка по умолчанию — `main` (или `master`). Создание ветки дает вам независимую линию развития: вы можете вносить изменения, не затрагивая `main`.

```bash
git branch feature-x              # create a branch
git checkout feature-x            # switch to it
git checkout -b feature-x         # create and switch in one step
git branch -d feature-x           # delete branch (after merging)
git branch -a                     # list all branches (local + remote)
```

- **Когда разветвляться**: всегда. Никогда не принимайте непосредственно `main`. У каждой функции, исправления ошибок или эксперимента есть своя ветка. Это обеспечивает стабильность и возможность развертывания `main`.

### Стратегии ветвления

- **Ветви функций** (наиболее распространенные): каждая функция/исправление получает ветвь от `main`. Когда закончите, откройте запрос на включение (PR), чтобы выполнить обратное слияние. Простой, работает для большинства команд.

- **Разработка на основе магистралей**: разработчики часто (несколько раз в день) используют `main`, используя флажки функций, чтобы скрыть незавершенную работу. Предпочитается командами, которые развертывают постоянно (Google, Facebook). Требуется отличный CI/CD.

- **Gitflow**: отдельные ветки для функций, выпусков и исправлений. Более сложный, лучше подходит для программного обеспечения с версионными выпусками (мобильные приложения, пакетное программное обеспечение). Слишком много для большинства проектов машинного обучения.

– Для команд ML лучше всего подходят **функциональные ветки** с кратковременными ветками (слияние в течение 1–3 дней). Долгоживущие ветки расходятся с `main` и создают болезненные конфликты слияния.

## Слияние и перебазирование

- **Merge** создает новую «фиксацию слияния», которая объединяет две ветки:

```bash
git checkout main
git merge feature-x
```

- При этом сохраняется полная история: вы можете видеть, что работа происходила в ветке и когда она была объединена. У коммита слияния есть два родителя.

- **Rebase** воспроизводит коммиты вашей ветки поверх целевой ветки:

```bash
git checkout feature-x
git rebase main
```

- Это переписывает историю: коммиты вашей ветки получают новые хеши, как если бы вы начали свою работу с текущей подсказки `main`. В результате получается линейная история (без коммитов слияния), которую легче читать.

- **Когда использовать**:
    - **Перебазируйте** для обновления вашей ветки функций последними изменениями `main` (сохраняет вашу ветку чистой и актуальной).
    - **Объединить** для интеграции вашей функциональной ветки в `main` (сохраняет историю ветки).
    - **Никогда не перебазируйте коммиты, которые были отправлены и переданы** другим. Перебазирование переписывает историю; если кто-то другой основывает работу на исходных коммитах, перебазирование вызывает хаос.

## Разрешение конфликтов- **Конфликт** возникает, когда две ветки изменяют одну и ту же строку одного и того же файла. Git не может автоматически решить, какое изменение сохранить, и просит вас разрешить его вручную.

```
<<<<<<< HEAD
learning_rate = 0.001
=======
learning_rate = 0.0005
>>>>>>> feature-x
```

- Между `<<<<<<< HEAD` и `=======` находится текущая версия ветки. Между `=======` и `>>>>>>> feature-x` находится версия входящей ветки. Вы решаете, что оставить (или объединить), удалить маркеры, сохранить и `git add` разрешенный файл.

- **Подводная ошибка**: не оставляйте маркеры конфликта в зафиксированных файлах. Это буквальный текст, который сломает ваш код. Всегда ищите `<<<<<<<` после разрешения.

- **Уменьшение конфликтов**: держите ветки недолговечными, часто объединяйте `main` в свою ветку и избегайте одновременного редактирования одного и того же файла несколькими людьми.

## Написание хороших сообщений о коммитах

- Сообщение о фиксации предназначено для вас в будущем и ваших товарищей по команде. «исправить ошибку» вам ни о чем не говорит. «Исправить погрешность в расчете размера пакета, которая вызывала OOM при обучении с 8 графическими процессорами», расскажет вам обо всем.

- **Формат**:

```
Short summary (50 chars or less, imperative mood)

Longer description if needed. Explain WHY, not WHAT
(the diff shows what changed). Wrap at 72 characters.

Fixes #123
```

– **Повелительное наклонение**: «Добавить функцию», а не «Добавлена функция» или «Добавляет функцию». Прочтите его как завершение предложения: «Если этот коммит будет применен, он **добавит функцию**».

- **Атомарные коммиты**: каждый коммит должен делать одно действие. «Добавить загрузчик данных» — это один коммит. «Добавить загрузчик данных, исправить несвязанную ошибку и обновить README» должно быть три коммита. Это делает возможным `git bisect` (поиск того, какой коммит привел к ошибке).

## Запросы на извлечение и проверка кода

- **pull request (PR)** предлагает объединить ветку с `main`. Это шлюз для проверки кода: коллеги читают ваши изменения, предлагают улучшения и одобряют их перед слиянием.

- **Хорошие практики PR**:
    - Делайте PR небольшими (до 400 строк изменений). Крупные PR получают одобрение, потому что никто не хочет проверять 2000 строк.
    - Напишите четкое описание: что изменилось, почему и как это проверить.
    - Ссылка на проблему или заявку, которая послужила причиной изменения.
    - Оперативно отвечайте на комментарии.
    - Сжатие тривиальных коммитов перед слиянием (чтобы у `main` была чистая история).

- **Проверка кода не направлена ​​на поиск ошибок** (это делают тесты). Речь идет об обмене знаниями (рецензент изучает кодовую базу), обратной связи по дизайну (правильный ли это подход?) и поддержании стандартов (именование, стиль, архитектура).

## .gitignore

— Файл `.gitignore` сообщает git, какие файлы следует исключить из отслеживания. Для проектов ML:

```gitignore
# Python
__pycache__/
*.pyc
*.egg-info/
.venv/
env/

# Data and models (too large for git)
data/
*.csv
*.parquet
models/
*.pt
*.onnx
*.bin
checkpoints/

# Secrets
.env
*.pem
credentials.json

# IDE
.vscode/
.idea/
*.swp

# OS
.DS_Store
Thumbs.db

# Jupyter
.ipynb_checkpoints/

# Experiment outputs
wandb/
mlruns/
outputs/
logs/
```

- **Подводная ошибка**: добавление файла в `.gitignore` после его фиксации не приводит к его удалению из репозитория. Вам также необходимо `git rm --cached file`, чтобы отменить его отслеживание. Файл останется в истории навсегда, если вы не перепишете историю (что беспорядочно).

## Git для машинного обучения

- ML создает проблемы, с которыми не сталкивается традиционное программное обеспечение:

– **Большие файлы**: размеры наборов данных и моделей составляют гигабайты и более. Git предназначен для текстовых файлов (исходный код), а не двоичных объектов. Решения:
    - **Git LFS** (хранилище больших файлов): отслеживает указатели в git, сохраняет файлы на отдельном сервере. Простой, но имеет ограничения на хранилище/пропускную способность на GitHub.
    - **DVC** (контроль версий данных): управляет файлами данных и моделей отдельно от git, используя удаленное хранилище (S3, GCS). Работает как git для данных: `dvc add data.csv`, `dvc push`, `dvc pull`.

– **Отслеживание экспериментов**: какие фиксации + какие гиперпараметры + какие данные и какие метрики создают? Git отслеживает код, но не весь контекст эксперимента.
    - **Вес и предвзятость (W&B)**: записывает метрики, гиперпараметры, информацию о системе и ссылки на коммит git. Предоставляет информационные панели для сравнения запусков.
    - **MLflow**: отслеживание экспериментов с открытым исходным кодом с помощью реестра моделей. Регистрирует параметры, метрики и артефакты.
    - **Простой подход**: запишите хэш git в свой обучающий скрипт: `git_hash = subprocess.check_output(['git', 'rev-parse', 'HEAD']).strip()`. Сохраните его вместе с результатами.- **Контрольный список воспроизводимости** (что отслеживать для каждого эксперимента):
    - Хэш коммита Git (точная версия кода)
    - Конфигурационный файл/гиперпараметры
    - Случайные семена
    - Версии Python и библиотеки (`pip freeze`)
    - Версия данных (хэш DVC или тег версии набора данных)
    - Аппаратное обеспечение (тип графического процессора, количество графических процессоров)

```bash
# Quick reproducibility snapshot
echo "Commit: $(git rev-parse HEAD)" > experiment_info.txt
echo "Branch: $(git branch --show-current)" >> experiment_info.txt
echo "Dirty: $(git status --porcelain | wc -l) files" >> experiment_info.txt
pip freeze >> experiment_info.txt
nvidia-smi >> experiment_info.txt
```
