# Проектирование и шаблоны кодовой базы

*Хороший дизайн кодовой базы — это то, что отличает исследовательский прототип от производственного программного обеспечения. В этом файле описывается структура проекта, принципы чистого кода, шаблоны проектирования, относящиеся к машинному обучению, управление конфигурацией, ведение журналов, дизайн API и упаковка*.

— Большая часть кода машинного обучения начинается с блокнота Jupyter. Блокнот растет, копируется, модифицируется, делится и в конечном итоге превращается в неуправляемый клубок глобальных переменных, мертвых ячеек и магических чисел. **Проектирование кодовой базы** – это дисциплина, позволяющая организовать код таким образом, чтобы он оставался понятным и допускающим модификацию по мере роста проекта.

- Речь идет не о следовании правилам ради них самих. Речь идет о сокращении времени между «я хочу изменить X» и «X изменено и работает». В хорошо спроектированной кодовой базе это время составляет минуты. В плохо спроектированном — это дни археологии через недокументированные спагетти.

## Структура проекта

- Согласованная структура проекта позволяет любому (включая вас в будущем) мгновенно перемещаться по базе кода.

```
my_project/
├── src/my_project/       # source code (importable package)
│   ├── __init__.py
│   ├── data/             # data loading and preprocessing
│   │   ├── __init__.py
│   │   ├── dataset.py
│   │   └── transforms.py
│   ├── models/           # model architectures
│   │   ├── __init__.py
│   │   ├── transformer.py
│   │   └── layers.py
│   ├── training/         # training loops, optimisers
│   │   ├── __init__.py
│   │   ├── trainer.py
│   │   └── losses.py
│   └── utils/            # shared utilities
│       ├── __init__.py
│       └── logging.py
├── configs/              # configuration files
│   ├── base.yaml
│   └── experiment_1.yaml
├── scripts/              # entry points (train, evaluate, serve)
│   ├── train.py
│   ├── evaluate.py
│   └── serve.py
├── tests/                # test files (mirrors src/ structure)
│   ├── test_dataset.py
│   ├── test_model.py
│   └── test_trainer.py
├── notebooks/            # exploration only (not production code)
├── pyproject.toml        # project metadata and dependencies
├── README.md
├── .gitignore
└── Dockerfile
```

- **Макет `src/`**: размещение исходного кода в папке `src/my_project/` предотвращает случайный импорт из текущего каталога (что маскирует ошибки импорта, которые могут возникнуть в рабочей среде). Установите с помощью `pip install -e .` для разработки.

- **Монорепозиторий или несколько репозиториев**: **монорепо** хранит все связанные проекты в одном репозитории (более простые изменения между проектами, общий CI). **Мультирепозиторий** предоставляет каждому проекту собственный репозиторий (более четкие границы, независимое управление версиями). Большинство команд ML начинают с монорепозитория и при необходимости разделяют его позже.

- **Скрипты или библиотека**: сохраняйте точки входа (`train.py`, `evaluate.py`) в `scripts/`. Сохраняйте многоразовую логику в `src/`. Сценарий обучения должен состоять примерно из 50 строк: конфигурация анализа, сборка набора данных, сборка модели, сборка тренера, обучение. Вся сложность живет в библиотеке.

## Принципы чистого кода

– **Именование**: самое эффективное, что вы можете сделать. Переменная с именем `x` требует, чтобы вы прочитали окружающий код, чтобы понять ее. Переменная с именем `learning_rate` является самодокументируемой.

```python
# BAD
def proc(d, n, lr):
    for i in range(n):
        for k, v in d.items():
            v -= lr * g[k]

# GOOD
def update_parameters(parameters, num_steps, learning_rate):
    for step in range(num_steps):
        for name, param in parameters.items():
            param -= learning_rate * gradients[name]
```

- **Принцип единой ответственности**: каждая функция/класс выполняет одно действие. Функция под названием `load_data_and_train_model` выполняет две вещи, и ее следует разделить. Это делает каждую часть независимо тестируемой, многократно используемой и понятной.

- **DRY (Не повторяйся)** — но не преждевременно. Если вы скопируете и вставите код три раза, извлеките его в функцию. Но не создавайте абстракцию для кода, который вы использовали только один раз. Преждевременная абстракция хуже дублирования: она усложняет работу без доказанной пользы.

```python
# Premature abstraction (one use case, over-engineered)
class AbstractDataTransformPipelineFactory:
    ...

# Just right (direct, clear, used in three places)
def normalise_image(image, mean, std):
    return (image - mean) / std
```

- **Магические числа**: никогда не используйте необъяснимые литеральные значения.

```python
# BAD
if len(batch) > 32:
    split_batch(batch, 32)

# GOOD
MAX_BATCH_SIZE = 32
if len(batch) > MAX_BATCH_SIZE:
    split_batch(batch, MAX_BATCH_SIZE)
```

- **Функции должны быть короткими**: если функция не умещается на одном экране (~30 строк), возможно, она делает слишком много. Извлекайте логические фрагменты во вспомогательные функции с описательными именами. Тело функции тогда читается как краткое описание.

## Шаблоны проектирования для машинного обучения

— Шаблоны проектирования — это многократно используемые решения распространенных проблем. Вот те, которые наиболее актуальны для кодовых баз ML:

- **Фабричный шаблон**: создание объектов без указания точного класса. Полезно, когда в вашей конфигурации указано `model: "transformer"` и вам нужно создать экземпляр правильного класса:

```python
MODEL_REGISTRY = {
    "transformer": TransformerModel,
    "cnn": CNNModel,
    "mlp": MLPModel,
}

def build_model(config):
    model_cls = MODEL_REGISTRY[config["model"]]
    return model_cls(**config["model_params"])
```

- Это отделяет сценарий обучения от конкретных реализаций модели. Добавление новой модели означает добавление одной строки в реестр, а не изменение цикла обучения.

- **Шаблон стратегии**: меняйте алгоритмы во время выполнения. Полезно при потерях, оптимизаторах, планировщиках:

```python
LOSS_FUNCTIONS = {
    "mse": nn.MSELoss,
    "cross_entropy": nn.CrossEntropyLoss,
    "focal": FocalLoss,
}

loss_fn = LOSS_FUNCTIONS[config["loss"]]()
```

- **Шаблон наблюдателя** (обратные вызовы/перехватчики): позволяют модулям реагировать на события без жесткой связи. Среды обучения (PyTorch Lightning, Keras) широко используют обратные вызовы:

```python
class EarlyStopping:
    def __init__(self, patience=5):
        self.patience = patience
        self.best_loss = float('inf')
        self.counter = 0

    def on_epoch_end(self, epoch, val_loss):
        if val_loss < self.best_loss:
            self.best_loss = val_loss
            self.counter = 0
        else:
            self.counter += 1
            if self.counter >= self.patience:
                return "stop"
```

- **Внедрение зависимостей**: передайте зависимости в функцию/класс, а не создайте их внутри. Это упрощает тестирование (внедрение макета) и гибкость настройки:

```python
# BAD: hard-coded dependency
class Trainer:
    def __init__(self):
        self.logger = WandbLogger()  # cannot test without W&B

# GOOD: injected dependency
class Trainer:
    def __init__(self, logger):
        self.logger = logger  # can inject any logger, including a mock
```

## Управление конфигурацией

— Жесткое кодирование гиперпараметров, путей к файлам и настроек модели делает эксперименты невоспроизводимыми, а модификации — болезненными. **Экранализация конфигурации** в файлы.- **YAML** — наиболее распространенный формат конфигураций ML:

```yaml
# configs/experiment_1.yaml
model:
  name: transformer
  d_model: 512
  n_heads: 8
  n_layers: 6

training:
  batch_size: 64
  learning_rate: 3e-4
  max_epochs: 100
  early_stopping_patience: 10

data:
  train_path: /data/train.parquet
  val_path: /data/val.parquet
  max_seq_length: 512
```

- **Hydra** (Facebook) — это платформа конфигурации, которая поддерживает композицию (объединение базовой конфигурации с переопределениями, специфичными для эксперимента), переопределения командной строки (`python train.py training.lr=1e-3`) и многопроходную обработку (очистку гиперпараметров).

- **argparse** проще для скриптов с несколькими параметрами:

```python
import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--lr", type=float, default=3e-4)
parser.add_argument("--batch-size", type=int, default=64)
parser.add_argument("--config", type=str, default="configs/base.yaml")
args = parser.parse_args()
```

– **Рекомендация**: используйте базовую конфигурацию со всеми настройками по умолчанию и конфигурации для каждого эксперимента, которые переопределяют только те изменения, которые были изменены. Отслеживайте конфигурацию каждого эксперимента вместе с его результатами.

## Ведение журнала и наблюдаемость

- Операторы `print` предназначены для отладки. **Журналирование** предназначено для производства:

```python
import logging

logger = logging.getLogger(__name__)
logger.setLevel(logging.INFO)

logger.debug("Batch loaded: %d samples", len(batch))     # noisy, for debugging
logger.info("Epoch %d: loss=%.4f, lr=%.6f", epoch, loss, lr)  # normal operation
logger.warning("GPU memory >90%%, consider reducing batch size")
logger.error("Failed to load checkpoint: %s", path)       # recoverable error
logger.critical("CUDA out of memory, aborting")            # fatal
```

- **Почему бы не распечатать**: ведение журнала поддерживает уровни (фильтрация отладочных сообщений в рабочей среде), форматирование (временные метки, имена модулей) и обработчики (запись в файл, отправка в систему мониторинга) без изменения вызовов журнала.

– **Структурированное ведение журнала** выводит машиночитаемые форматы (JSON) вместе с сообщениями, читаемыми человеком. Это позволяет осуществлять поиск и оповещения по определенным полям:

```python
logger.info("training_step", extra={
    "epoch": 5, "step": 1200, "loss": 0.0342, "lr": 2.1e-4
})
```

## Дизайн API

– Если ваша модель будет использоваться другими сервисами (веб-приложением, мобильным приложением, другим конвейером машинного обучения), ей потребуется **API** (интерфейс прикладного программирования).

- **REST API** используют методы HTTP: `GET` для чтения, `POST` для создания/прогнозирования, `PUT` для обновления, `DELETE` для удаления. Конечные точки следуют именованию на основе ресурсов:

```
POST /api/v1/predict          # send input, get prediction
GET  /api/v1/models           # list available models
GET  /api/v1/models/{id}      # get model details
POST /api/v1/models/{id}/predict  # predict with a specific model
```

- **FastAPI** — это платформа Python для обслуживания машинного обучения:

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class PredictRequest(BaseModel):
    text: str

class PredictResponse(BaseModel):
    label: str
    confidence: float

@app.post("/predict", response_model=PredictResponse)
async def predict(request: PredictRequest):
    result = model.predict(request.text)
    return PredictResponse(label=result.label, confidence=result.score)
```

— FastAPI автоматически генерирует документацию по API (пользовательский интерфейс Swagger по адресу `/docs`), проверяет ввод/вывод с помощью моделей Pydantic и поддерживает асинхронность для высокой пропускной способности.

- **gRPC** быстрее, чем REST, для внутренней связи между службами. Он использует буферы протокола (двоичная сериализация, меньше и быстрее, чем JSON) и поддерживает потоковую передачу. Используется TensorFlow Serving, Triton Inference Server и многими микросервисными архитектурами.

## Упаковка и распространение

- Возможность установки вашего кода в виде пакета позволяет другим (и вашим собственным сценариям) импортировать его без проблем:

```toml
# pyproject.toml
[project]
name = "my-ml-project"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = [
    "torch>=2.0",
    "jax>=0.4",
    "pydantic>=2.0",
]

[project.optional-dependencies]
dev = ["pytest", "ruff", "mypy"]

[build-system]
requires = ["setuptools>=64"]
build-backend = "setuptools.backends._legacy:_Backend"
```

```bash
pip install -e ".[dev]"    # install in editable mode with dev dependencies
```

- **Редактируемая установка** (`-e`): изменения в исходном коде немедленно отражаются без переустановки. Незаменим во время разработки.

- **Закрепление зависимостей**: `requirements.txt` с точными версиями (`torch==2.2.1`, а не `torch>=2.0`) обеспечивает воспроизводимость. Используйте `pip freeze > requirements.txt`, чтобы запечатлеть текущую среду. Для более сложного управления зависимостями используйте `uv`, `poetry` или `pip-tools`.

## Работа с агентами кодирования AI

- Агенты ИИ-кодирования (Claude Code, GitHub Copilot, Cursor и т. д.) теперь являются частью профессионального инженерного рабочего процесса. При правильном использовании они значительно ускоряют разработку. При неправильном использовании они привносят малозаметные ошибки, подрывают ваше понимание собственной кодовой базы и создают ложное ощущение продуктивности.

- Правильная ментальная модель: **агент — быстрый, но неопытный парный программист**. Он может быстро писать код, знает синтаксис и стандартные шаблоны и прочитал больше документации, чем вы когда-либо сможете. Но он не понимает вашу конкретную систему, ваши бизнес-ограничения, ваши крайние случаи или «почему» ваших проектных решений. Вы старший инженер; агент - младший. Вы направляете, проверяете и берете на себя ответственность.

### Когда агенты превосходны

- **Шаблон и строительные леса**: создание файлов Dockerfile, конфигураций CI, тестовых приспособлений, определений классов данных, настроек argparse. Они следуют хорошо известным шаблонам, и их утомительно писать от руки. Позвольте агенту сгенерировать их, а затем проверьте их правильность.

- **Написание тестов**: опишите поведение функции, а агент создаст тестовые примеры. Он часто выявляет крайние случаи, которые вы можете пропустить (пустой ввод, отрицательные значения, Unicode). Всегда читайте сгенерированные тесты — они проверяют ваши предположения, а не только ваш код.- **Рефакторинг**: «извлечь этот блок в функцию», «преобразовать этот класс для использования классов данных», «добавить подсказки типов в этот модуль». Механические преобразования, цель которых ясна, а риск незначительных ошибок низок.

– **Исследование и создание прототипов**: «напишите быстрый сценарий для измерения задержки вывода» или «покажите мне, как использовать API токенизатора HuggingFace». Агент дает вам рабочую отправную точку быстрее, чем чтение документации.

- **Документация и строки документации**: агент может генерировать документацию на основе вашей структуры кода. Проверьте точность, но тяжелая работа автоматизирована.

- **Помощь в отладке**: вставьте обратную связь об ошибке и запросите диагностику. Агент часто может определить основную причину и предложить решение, особенно для распространенных проблем (несоответствие формы, ошибки импорта, нехватка памяти CUDA).

### Когда НЕ следует полагаться на агентов

- **Новые архитектурные решения**: если вы разрабатываете новый конвейер обучения, агент даст вам общий ответ. Он не знает ваших ограничений данных, требований к задержке или опыта команды. Используйте агента для реализации уже продуманного дизайна.

- **Код, критически важный для безопасности**: аутентификация, шифрование, очистка ввода. Агент может генерировать код, который выглядит правильно, но имеет незначительные уязвимости (инъекция SQL, небезопасные настройки по умолчанию, временные атаки). Код безопасности должен быть написан кем-то, кто понимает модель угроз, и проверен кем-то другим.

- **Внутренние циклы, критичные к производительности**: агент будет писать правильный, но простой код. Для ядер графического процессора, структур данных, критичных к памяти, или путей обслуживания, чувствительных к задержкам, вам необходимо понимать аппаратные ограничения (глава 13, глава 16) и сознательно оптимизировать их.

- **Код, который вы не понимаете**: если агент генерирует 200 строк, и вы не можете объяснить, что делает каждая строка, не фиксируйте ее. Теперь вы поддерживаете код, который не понимаете, и когда он сломается (а это произойдет), вы не сможете его отладить. Это наиболее распространенный и наиболее опасный вид отказа.

### Дисциплина обзора

- **Всегда читайте каждую строку** сгенерированного кода перед фиксацией. Это не является обязательным. Код агента — это черновик, а не готовый продукт. Относитесь к этому точно так же, как к запросу на включение от коллеги: рассмотрите его критически.

- **Что проверить**:
    - **Правильность**: действительно ли он делает то, что вы просили? Агенты часто решают задачу, слегка отличающуюся от той, которую вы задумали.
    - **Особые случаи**: обрабатывает ли он пустые входные данные, значения «Нет», отрицательные числа, очень большие входные данные? Агенты часто пропускают обработку крайних случаев.
    - **Галлюцинированные API**: агент может вызывать функции или использовать несуществующие параметры, особенно для новых или менее распространенных библиотек. Убедитесь, что каждый вызов API реален.
    - **Чрезмерное проектирование**: агенты склонны создавать больше кода, чем необходимо. Решение задачи из 10 строк в 50 строк усложняет задачу, но не приносит пользы. Упрощайте безжалостно.
    - **Безопасность**: жестко запрограммированные секреты, несанкционированный пользовательский ввод, небезопасные настройки по умолчанию. Агент не мыслит враждебно.
    – **Согласованность стиля**: соответствует ли сгенерированный код соглашениям вашего проекта (именование, шаблоны, обработка ошибок)?

### Как писать хорошие подсказки

- Качество результатов работы агента прямо пропорционально качеству вашей инструкции. Неясные подсказки получают неясный код.

- **Плохо**: «написать загрузчик данных».
- **Хорошо**: «Напишите PyTorch DataLoader для CSV-файла со столбцами «текст» и «метка». Токенизируйте текст с помощью токенизатора HuggingFace «bert-base-uncased» с max_length = 512. Возвращайте input_ids, focus_mask и label как тензоры. Обрабатывайте случай, когда в CSV отсутствуют значения в столбце метки, пропуская эти строки.

– **Предоставьте контекст**: расскажите агенту о структуре вашего проекта, существующем коде, ограничениях и соглашениях. Чем больше контекста, тем лучше результат.

- **Укажите ограничения**: «использовать только стандартную библиотеку», «должен работать с Python 3.10», «не использовать глобальные переменные», «следовать существующему шаблону в `src/models/transformer.py`».

- **Попросите объяснений**: «Реализуйте X и объясните ключевые проектные решения». Это заставляет агента сформулировать свои рассуждения, что облегчает вам обнаружение ошибочных предположений.### Использование контроля качества для выявления ошибок агента

- Существующая инфраструктура качества (файл 04) фиксирует ошибки агентов так же, как и человеческие ошибки:

    - **Проверка типов (mypy)**: выявляет галлюцинированные сигнатуры API и несоответствия типов.
    - **Линтинг (ерш)**: выявляет неиспользуемые импорты, неопределенные переменные и нарушения стиля.
    - **Тесты (pytest)**: если код агента проходит ваш набор тестов, скорее всего, он правильный. Если у вас нет тестов, напишите их *прежде* просить агента реализовать эту функцию (разработка через тестирование особенно хорошо работает с агентами).
    - **Конвейер CI**: все вышеперечисленное выполняется автоматически при каждом коммите.

— Комбинация «агент пишет код» + «контролеры качества проверяют его» более продуктивна, чем каждый из них по отдельности. Агент работает быстро, но неряшливо; гейты основательные, но кода не пишут. Вместе вы получаете скорость и правильность.

### Ловушка продуктивности

— Самый большой риск программистов — это **иллюзия продуктивности**. Вы можете сгенерировать 500 строк кода за 10 минут. Но если вы потратите 2 часа на отладку этих 500 строк, потому что не понимаете их, вы будете медленнее, чем писать 200 строк самостоятельно за 30 минут.

- Истинная продуктивность работы агентов достигается за счет:
    1. **Все под контролем**: вы решаете архитектуру, агент реализует реализацию.
    2. **Понимание того, что генерируется**: если вы не можете это объяснить, перепишите или попросите агента упростить.
    3. **Инвестирование в качественные шлюзы**: тесты, типы и анализ амортизируют затраты при каждом взаимодействии с агентом.
    4. **Использование агента для решения ваших слабых мест**: если вы хорошо разбираетесь в алгоритмах, но медленно пишете тесты, позвольте агенту писать тесты. Если вы быстро разбираетесь в коде пользовательского интерфейса, но не знакомы с запросами к базе данных, позвольте агенту составить SQL-код. Играйте на своих сильных сторонах, делегируйте свои пробелы.

— Инженеры, которые получают максимальную отдачу от агентов кодирования, — это те, кто уже умеет хорошо программировать. Агент усиливает ваши существующие навыки; оно не заменяет его. Понимание структур данных, алгоритмов, проектирования систем и разработки программного обеспечения (вся эта глава) — это то, что позволяет вам эффективно управлять агентом и критически оценивать его результаты.
