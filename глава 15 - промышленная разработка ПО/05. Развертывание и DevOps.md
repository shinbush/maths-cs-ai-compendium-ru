# Развертывание и DevOps

*Развертывание — это момент, когда ваша модель перестает быть исследовательским артефактом и становится продуктом. Этот файл охватывает Docker для машинного обучения, обслуживание моделей, отслеживание экспериментов, воспроизводимость, мониторинг в производстве, хранилища функций и оркестровку конвейеров — инфраструктуру, которая передает обученную модель из записной книжки миллионам пользователей.*

- Модель, которая работает только на вашем ноутбуке, является прототипом. Модель, которая надежно работает в любом масштабе, предоставляет прогнозы за миллисекунды, восстанавливается после сбоев и может обновляться без простоев, — это продукт. Разрыв между ними — **развертывание и DevOps**.

— Большинство инженеров ML тратят больше времени на развертывание, мониторинг и отладку производственных проблем, чем на обучение моделей. Понимание этой инфраструктуры не является обязательным для любого, кто создает настоящие системы машинного обучения.

## Докер для машинного обучения

- Концептуально мы рассмотрели контейнеры в главе 13 (ОС). Здесь мы сосредоточимся на практической стороне: написании Dockerfiles для рабочих нагрузок ML.

- **Dockerfile** — это рецепт создания образа контейнера:

```dockerfile
# Start from an official CUDA base image
FROM nvidia/cuda:12.1.0-cudnn8-runtime-ubuntu22.04

# System dependencies
RUN apt-get update && apt-get install -y \
    python3.11 python3-pip git \
    && rm -rf /var/lib/apt/lists/*

# Python dependencies (install separately for caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy source code (changes frequently, so this layer is last)
COPY src/ /app/src/
COPY configs/ /app/configs/
WORKDIR /app

# Entry point
CMD ["python3", "src/scripts/serve.py", "--config", "configs/serve.yaml"]
```

- **Кэширование слоев**: Docker кэширует каждый уровень. Если `requirements.txt` не изменился, `pip install` пропускается при перестроении. Поместите редко меняющиеся слои (системные пакеты, pip install) перед часто меняющимися (исходный код). Это превращает 10-минутную сборку в 10-секундную перестройку.

- **Доступ к графическому процессору**: используйте базовые образы `nvidia/cuda` и запускайте с `docker run --gpus all`. `nvidia-container-toolkit` обеспечивает передачу графического процессора от хоста к контейнеру.

- **Многоэтапные сборки** уменьшают размер образа за счет отделения среды сборки от среды выполнения:

```dockerfile
# Build stage: install build tools, compile dependencies
FROM python:3.11 AS builder
COPY requirements.txt .
RUN pip install --user -r requirements.txt

# Runtime stage: only runtime dependencies
FROM nvidia/cuda:12.1.0-cudnn8-runtime-ubuntu22.04
COPY --from=builder /root/.local /root/.local
COPY src/ /app/src/
ENV PATH=/root/.local/bin:$PATH
```

— Окончательный образ содержит только библиотеки времени выполнения, а не компиляторы, заголовки или инструменты сборки. Образ сборки размером 5 ГБ становится образом среды выполнения размером 2 ГБ.

- **Docker Compose** запускает многоконтейнерные настройки (модель сервера + балансировщик нагрузки + мониторинг):

```yaml
# docker-compose.yml
services:
  model:
    build: .
    ports:
      - "8080:8080"
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]
  prometheus:
    image: prom/prometheus
    ports:
      - "9090:9090"
```

## Обслуживание модели

– **Обслуживание модели** выполняет вывод как услугу: получает запросы, запускает модель, возвращает прогнозы.

- **FastAPI** (описанный в файле 03) — это самый простой подход для пропускной способности от низкой до средней. Для обеспечения высокой пропускной способности и оптимизации обслуживания с помощью графического процессора используйте специальные инструменты:

- **Сервер вывода Triton** (NVIDIA): обслуживает модели в форматах TensorRT, ONNX, PyTorch и TensorFlow. Особенности:
    - **Динамическая пакетная обработка**: собирает отдельные запросы и группирует их для повышения эффективности графического процессора. Поток одиночных запросов группируется в группы по 32, что значительно повышает пропускную способность.
    - **Ансамбли моделей**: объединяйте несколько моделей (препроцессор → модель → постпроцессор) в одном запросе.
    - **Обслуживание нескольких моделей**: обслуживание нескольких моделей на одном графическом процессоре, совместное использование ресурсов.
    - **Параллельное выполнение модели**: параллельное выполнение нескольких запросов на вывод на одном графическом процессоре.

- **TorchServe** (PyTorch): обслуживает модели PyTorch с помощью API REST/gRPC. Поддерживает управление версиями модели, A/B-тестирование и пользовательские обработчики.

- **vLLM**: специализируется на обслуживании LLM. Реализует PagedAttention (эффективное управление кэшем KV), непрерывную пакетную обработку и тензорный параллелизм между графическими процессорами. Обеспечивает в 10–20 раз более высокую пропускную способность, чем простое обслуживание больших языковых моделей.

- **Cactus** ([github.com/cactus-compute/cactus](https://github.com/cactus-compute/cactus)): механизм искусственного интеллекта с малой задержкой для обслуживания на мобильных устройствах и периферийных устройствах. Cactus предоставляет **OpenAI-совместимый API** (завершение чата, потоковая передача, вызов инструментов, транскрипция, встраивание, RAG, видение), который полностью работает на устройстве, с автоматическим **обратным переходом в облако**, когда локальная модель не может обработать запрос. Эта гибридная архитектура означает, что код вашего приложения использует один и тот же API независимо от того, выполняется ли логический вывод локально или в облаке — механизм принимает решение на основе достоверности модели и возможностей устройства. Доступны SDK для Python, Swift, Kotlin, Flutter, React Native и Rust с предварительно преобразованными весами моделей на HuggingFace. Поддерживает мультимодальный вывод (LLM, зрение, речь) с помощью специальных ядер ARM SIMD для быстрого вывода на процессорах ARM и сопоставления памяти с нулевым копированием для снижения использования оперативной памяти в 10 раз (глава 16, глава 17).- **Оптимизация формата модели**:
    - **ONNX**: открытый формат для совместимости. Экспорт из PyTorch/TensorFlow, запуск где угодно.
    - **TensorRT**: оптимизатор NVIDIA. Объединяет слои, выбирает оптимальные ядра, квантует веса. Обычно в 2–5 раз быстрее, чем PyTorch на графических процессорах NVIDIA.
    - **GGUF/GGML**: форматы для вывода с эффективностью использования ЦП, популярные для запуска LLM на потребительском оборудовании.

## Отслеживание экспериментов

— Без отслеживания экспериментов исследование ML сводится к следующему: «Я думаю, что модель прошлого вторника с той конфигурацией, в которой я что-то изменил, была лучшей, но я не помню, что я изменил».

- **Weights & Biases (W&B)**: самый популярный трекер экспериментов. Запишите что-нибудь из вашего сценария обучения:

```python
import wandb

wandb.init(project="my-project", config={
    "model": "transformer",
    "lr": 3e-4,
    "batch_size": 64,
})

for epoch in range(num_epochs):
    train_loss = train_one_epoch()
    val_loss = validate()

    wandb.log({
        "train/loss": train_loss,
        "val/loss": val_loss,
        "epoch": epoch,
    })

    # Log model as artifact
    if val_loss < best_loss:
        wandb.save("best_model.pt")

wandb.finish()
```

- W&B предоставляет: информационные панели для сравнения прогонов, инструменты очистки гиперпараметров, реестр моделей, управление версиями наборов данных и совместную работу группы.

- **MLflow**: альтернатива с открытым исходным кодом. Запускается локально или на сервере:

```python
import mlflow

mlflow.set_experiment("my-experiment")

with mlflow.start_run():
    mlflow.log_params({"lr": 3e-4, "batch_size": 64})
    mlflow.log_metric("val_loss", 0.042, step=epoch)
    mlflow.pytorch.log_model(model, "model")
```

- **Реестр моделей**: центральное хранилище обученных моделей с контролем версий, промежуточной версией (разработка → промежуточная версия → производство) и метаданными. И W&B, и MLflow предоставляют реестры. Реестр отвечает: «Какая модель в настоящее время находится в производстве, кто ее обучил, какова точность ее проверки и какой код/данные ее создали?»

## Воспроизводимость

- Воспроизводимость означает: при использовании одного и того же кода, данных и конфигурации создается одна и та же модель. В машинном обучении это на удивление сложно из-за недетерминированности операций графического процессора, перетасовки данных и накопления чисел с плавающей запятой.

- **Контрольный список воспроизводимости**:

| Что | Как |
|------|-----|
| Версия кода | Хеш коммита Git |
| Конфигурация/гиперпараметры | Файл конфигурации (с версией в git или зарегистрированной в W&B) |
| Случайные семена | Установить и зарегистрировать все начальные значения (Python, NumPy, PyTorch, CUDA) |
| Версия данных | Хэш DVC, тег версии набора данных или версия объекта S3 |
| Зависимости | `pip freeze`, хэш образа Docker или файл блокировки |
| Аппаратное обеспечение | Тип графического процессора, количество графических процессоров, версия CUDA |
| Недетерминизм | `torch.backends.cudnn.deterministic = True` (медленнее, но воспроизводимо) |

- **Закрепление всего**: `pip install torch==2.2.1`, а не `torch>=2.0`. Небольшое изменение версии может изменить числовое поведение, реализацию оптимизатора или гиперпараметры по умолчанию.

- **Docker для воспроизводимости**: образ Docker закрепляет операционную систему, системные библиотеки, версию Python и пакеты pip. Хэш изображения представляет собой полный отпечаток среды. Если вы можете воспроизвести образ Docker, вы сможете воспроизвести обучение.

## Мониторинг в производстве

— Развертывание модели — это не конец, это начало нового комплекса проблем. Модели со временем ухудшаются по мере изменения реального мира (**дрейф концепции**) и по мере изменения распределения входных данных (**дрейф данных**).

- **Что отслеживать**:

    - **Задержка**: сколько времени занимает вывод? Отслеживайте p50 (медиана), p95 и p99. Значение p99, равное 500 мс, означает, что 1 из 100 пользователей ждет полсекунды, что может быть неприемлемо.

    - **Пропускная способность**: сколько запросов в секунду? Соответствует ли система спросу?

    - **Коэффициент ошибок**: какая часть запросов завершается неудачей (исключения, тайм-ауты, неверные входные данные)?

    – **Показатели модели**: точность, точность, отзыв на контрольном наборе. Если в рабочей среде доступны помеченные данные (например, исправления пользователей), отслеживайте онлайн-показатели.

    - **Дрейф данных**: изменилось ли распределение входящих данных? Модель, обученная на дневных фотографиях, может потерпеть неудачу на ночных фотографиях. Статистические тесты (тест KS, PSI) сравнивают тренировочное распределение с реальным распределением.

    - **Дрейф функций**: изменилось ли распределение отдельных функций? Функция, которая обычно распространялась во время обучения, но теперь является бимодальной, сигнализирует о проблеме с конвейером данных.

- **Инструменты**:
    - **Prometheus** + **Grafana**: стандарт мониторинга инфраструктуры. Prometheus собирает метрики, Grafana визуализирует их на дашбордах с оповещениями.
    - **Очевидно, ИИ**: мониторинг ОД с открытым исходным кодом. Создает отчеты о смещении данных, производительности модели и качестве данных.

- **Оповещения**: не просто размещайте их на панели управления — настройте автоматические оповещения. «Если задержка p99 превышает 200 мс в течение 5 минут, отправьте уведомление Slack». «Если показатель отклонения данных превышает пороговое значение, сообщите об этом дежурному инженеру».

## Магазины функций– **Хранилище функций** – это централизованное хранилище предварительно вычисленных функций, совместно используемое для обучения и обслуживания. Он решает две проблемы:

    - **Несовпадение между обучением и обслуживанием**: функции, используемые во время обучения, должны быть идентичны тем, которые используются во время обслуживания. Если при обучении используется `user_age_at_signup`, вычисленный одним способом, а при обслуживании — другим, то прогнозы модели явно неверны.

    – **Повторное использование функций**: несколько моделей часто используют одни и те же функции (демографические данные пользователей, встраивание элементов, агрегированная статистика). Вычисление их один раз и совместное использование позволяет избежать дублирования и несогласованности.

- **Feast** — самый популярный магазин функций с открытым исходным кодом. Он управляет онлайн-функциями (с низкой задержкой, обслуживаются из Redis или DynamoDB) и автономными функциями (пакетными, хранящимися в хранилищах данных для обучения).

- Хранилища функций имеют решающее значение для систем рекомендаций, обнаружения мошенничества и любых приложений, в которых функции вычисляются из конвейеров необработанных данных.

## Конвейерная оркестровка

— Производственная система ML — это не просто модель. Это **конвейер**: прием данных → предварительная обработка → вычисление функций → обучение → оценка → развертывание → мониторинг. Каждый шаг зависит от предыдущего, может завершиться сбоем независимо и может потребоваться выполнение по разным расписаниям.

- **Оркестраторы** управляют этими конвейерами:

- **Apache Airflow**: стандарт оркестровки конвейеров данных. DAG (направленные ациклические графы) определяют зависимости задач. Каждая задача выполняется независимо, может быть повторена в случае сбоя и контролируется через веб-интерфейс.

```python
# airflow DAG example (simplified)
from airflow import DAG
from airflow.operators.python import PythonOperator

dag = DAG("training_pipeline", schedule="@daily")

preprocess = PythonOperator(task_id="preprocess", python_callable=preprocess_data, dag=dag)
train = PythonOperator(task_id="train", python_callable=train_model, dag=dag)
evaluate = PythonOperator(task_id="evaluate", python_callable=evaluate_model, dag=dag)
deploy = PythonOperator(task_id="deploy", python_callable=deploy_model, dag=dag)

preprocess >> train >> evaluate >> deploy
```

- **Kubeflow Pipelines**: оркестровка в Kubernetes, специфичная для машинного обучения. Каждый шаг выполняется в контейнере, ресурсы графического процессора выделяются по требованию, а эксперименты отслеживаются автоматически.

- **Prefect** и **Dagster**: современные альтернативы Airflow с улучшенным интерфейсом разработчика, собственными API-интерфейсами Python и встроенной системой передачи данных.

– **Когда проводить оркестрацию**: когда ваш конвейер состоит из более чем 2–3 шагов, работает по расписанию, включает в себя несколько команд или служб или требует автоматического восстановления после сбоев. Для обучения с одним сценарием оркестратор не требуется. Ежедневный конвейер переобучения, который получает данные из 5 источников, обучает 3 модели, оценивает их и развертывает лучшую из них.
