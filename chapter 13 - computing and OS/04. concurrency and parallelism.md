# Параллелизм и параллелизм

* Параллелизм и параллелизм — это то, как программы выполняют несколько задач одновременно. В этом файле описаны различия между параллелизмом и параллелизмом, примитивы синхронизации, классические проблемы параллелизма, взаимоблокировки, структуры данных без блокировок, модели параллельного программирования, асинхронное программирование и законы масштабирования, концепции, лежащие в основе многопоточных серверов, распределенное обучение и все современные приложения.*

- Одно ядро ЦП одновременно выполняет одну инструкцию. Но современные системы имеют 8, 64 или даже тысячи ядер (GPU). И даже на одном ядре мы хотим выполнять несколько задач: загружать файл, рендерить пользовательский интерфейс и обрабатывать пользовательский ввод. **Конкуренция** и **параллелизм** — две стратегии управления несколькими действиями.

## Параллелизм против параллелизма

![Concurrency interleaves tasks on one core; parallelism runs tasks simultaneously on multiple cores](../images/concurrency_vs_parallelism.svg)

- **Параллелизм** подразумевает *управление* несколькими задачами. Задачи выполняются за счет чередования: какое-то время выполняется задача A, затем задача B, а затем обратно к A. На одном ядре параллелизм создает иллюзию одновременного выполнения. Задачи не являются по-настоящему одновременными; они по очереди.

- **Параллелизм** подразумевает *выполнение* нескольких задач одновременно. Благодаря ядрам $n$ задачи $n$ могут выполняться одновременно. Параллелизм требует наличия нескольких аппаратных исполнительных блоков.

- Аналогия: параллелизм: один повар поочередно нарезает овощи и помешивает их в кастрюле. Параллелизм — два повара, каждый из которых одновременно выполняет одну задачу. Система может быть одновременной, но не параллельной (одно ядро, чередующиеся задачи), параллельной, но не параллельной (несколько ядер, выполняющих независимые программы без взаимодействия), или и той, и другой (несколько ядер, выполняющих чередующиеся взаимодействующие задачи).

- В машинном обучении параллелизм проявляется при загрузке данных (перекрытие предварительной обработки данных с вычислениями на графическом процессоре), а параллелизм проявляется при распределенном обучении (несколько графических процессоров одновременно вычисляют градиенты, глава 6).

## Примитивы синхронизации

- Когда несколько потоков совместно используют данные, **синхронизация** предотвращает возникновение гонок. Состояние гонки возникает, когда результат зависит от непредсказуемого порядка выполнения потока.

- Рассмотрим два потока, каждый из которых увеличивает общий счетчик: `counter += 1`. На самом деле это три операции: (1) чтение счетчика, (2) добавление 1, (3) запись счетчика. Если оба потока читают одно и то же значение (скажем, 5), оба добавляют 1 и оба записывают 6, счетчик оказывается на 6 вместо правильных 7. Одно приращение теряется.

- **мьютекс** (блокировка взаимного исключения) гарантирует, что только один поток сможет получить доступ к критическому разделу одновременно. Поток **захватывает** блокировку перед входом в критическую секцию и **освобождает** ее после. Любой другой поток, пытающийся получить удерживаемую блокировку, блокируется до тех пор, пока она не будет освобождена.

```
lock.acquire()
counter += 1      # only one thread at a time here
lock.release()
```

- Мьютексы корректны, но создают **конфликт**: если несколько потоков конкурируют за одну и ту же блокировку, они тратят время на ожидание, а не на вычисления. Это ограничивает масштабируемость. В крайнем случае, когда всем потокам требуется одна и та же блокировка, сериализуется вся программа.

- **Семафор** обобщает мьютекс. Счетный семафор поддерживает счетчик: `wait()` уменьшает счетчик (блокируется, если он становится отрицательным), а `signal()` увеличивает его. Семафор, инициализированный значением 1, ведет себя как мьютекс. Семафор, инициализированный как $n$, позволяет одновременно использовать до $n$ потоков в критическом разделе (полезно для пулов ресурсов, таких как соединения с базой данных).

- **условная переменная** позволяет потоку ждать, пока не будет выполнено определенное условие. Поток снимает блокировку, ожидает условной переменной и просыпается, когда другой поток сигнализирует об условии. Это позволяет избежать ожидания занятости (многократная проверка условия в цикле, напрасная нагрузка на процессор).

- **монитор** объединяет мьютекс с условными переменными и общими данными в единую абстракцию. Ключевое слово `synchronized` в Java и `threading.Condition` в Python реализуют семантику, подобную монитору.- **Блокировки чтения и записи** различают читателей (которые могут разделять доступ, поскольку чтение не изменяет данные) и писателей (которым нужен монопольный доступ). Несколько читателей могут удерживать блокировку одновременно, но писатель блокирует всех читателей и других писателей. Это оптимально, когда количество операций чтения намного превышает количество операций записи (например, кэшированная модель, обслуживающая прогнозы).

## Классические проблемы параллелизма

- **Производитель-потребитель** (ограниченный буфер): производители генерируют элементы и помещают их в буфер фиксированного размера; потребители удаляют товары. Проблемы: производители должны ждать, когда буфер заполнится, потребители должны дождаться, когда он опустеет, и оба должны избегать повреждения буфера.

— Решение использует два семафора (один считает пустые слоты, другой — полные слоты) плюс мьютекс для самого буфера. Это шаблон, лежащий в основе большинства очередей сообщений, систем журналирования и конвейеров данных.

- **Читатели-писатели**: несколько читателей могут читать одновременно, но писателям необходим эксклюзивный доступ. Проблема в справедливости: если читатели продолжат приходить, автор может умереть с голоду (никогда не получить доступа). Решения отдают приоритет читателям или писателям или справедливо чередуются.

- **Обедающие философы**: пять философов сидят вокруг стола с пятью вилками между ними. Каждому нужно две вилки, чтобы есть. Если все пятеро одновременно возьмут левую вилку, никто не сможет взять правую, и все умрут от голода (тупик). Решения включают в себя: брать обе вилки атомарно, ввести асимметрию (один философ первым берет правильную вилку) или использовать официанта (семафор ограничивает количество посетителей до 4).

## Тупик

- **Взаимная блокировка** возникает, когда каждый из набора потоков ожидает ресурса, удерживаемого другим потоком в наборе, создавая цикл зависимостей. Никто не может продолжить.

![Deadlock: Thread A holds Lock 1 and wants Lock 2, Thread B holds Lock 2 and wants Lock 1 — circular wait](../images/deadlock_cycle.svg)

- Четыре **необходимых условия** для тупиковой ситуации (все они должны выполняться одновременно):

    1. **Взаимное исключение**: ресурс может принадлежать только одному потоку.
    2. **Удерживать и ждать**: поток удерживает один ресурс, ожидая другого.
    3. **Нет вытеснения**: ресурсы нельзя принудительно забрать из потока.
    4. **Циклическое ожидание**: в графе ожидания существует цикл.

- **Предотвращение тупиковой ситуации** нарушает одно из четырех условий:
    - Устраните циклическое ожидание: настройте полный порядок ресурсов. Все потоки получают ресурсы в одном и том же порядке. Если каждый поток всегда получает блокировку A раньше блокировки B, цикл невозможен.
    - Устраните удержание и ожидание: требуйте, чтобы потоки запрашивали все ресурсы одновременно (атомарно).

- **Избежание тупиковой ситуации** динамически решает, может ли предоставление запроса на ресурс привести к тупиковой ситуации. **Алгоритм Банкира** поддерживает максимально возможные требования каждого потока и разрешает только те запросы, которые переводят систему в «безопасное состояние» (состояние, в котором все потоки могут в конечном итоге завершиться). Алгоритм $O(n^2 m)$ на запрос (потоки $n$, типы ресурсов $m$), что слишком дорого для большинства реальных систем.

- **Обнаружение взаимоблокировок** позволяет возникать взаимоблокировкам, затем обнаруживает их (находя циклы в графе ожидания) и восстанавливает (завершая поток или откатывая транзакцию).

- На практике большинство систем используют предотвращение (упорядочение ресурсов) для частых случаев и обнаружение для редких случаев. Системы баз данных являются классическим примером: они обнаруживают взаимоблокировки среди транзакций и прерывают одну из них, чтобы разорвать цикл.

## Структуры данных без блокировок и без ожидания

- Блокировки приводят к конфликтам, инверсии приоритетов и риску тупиковой ситуации. **Блокировочные** структуры данных полностью исключают блокировки, используя **атомарные операции**, предоставляемые аппаратным обеспечением.

- Ключевой атомарной операцией является **Сравнение-и-замена (CAS)**: атомарно проверяется, имеет ли ячейка памяти ожидаемое значение, и если да, заменяет ее новым значением. В псевдокоде:

```
CAS(address, expected, new_value):
    if *address == expected:
        *address = new_value
        return true
    else:
        return false
```

— CAS реализован как одна аппаратная инструкция, поэтому он атомарен даже без блокировок. Алгоритмы без блокировки используют CAS в цикле повторов: считывают текущее значение, вычисляют новое значение, пытаются выполнить CAS. Если другой поток тем временем изменил значение, CAS завершится сбоем, и поток повторит попытку.- **Без блокировки**: по крайней мере один поток выполняет определенное количество шагов (взаимная блокировка невозможна, но отдельные потоки могут повторять попытки бесконечно в условиях конкуренции).

- **Без ожидания**: каждый поток выполняет ограниченное количество шагов (самая надежная гарантия, но труднее всего ее достичь).

- Стеки, очереди и хеш-карты без блокировок широко используются в высокопроизводительных системах. Атомарные операции Java `ConcurrentHashMap` и Go построены на CAS.

## Модели параллельного программирования

- Параллелизм **совместной памяти**: все потоки обращаются к одному и тому же пространству памяти. Синхронизация является обязанностью программиста. **OpenMP** предоставляет директивы компилятора для распараллеливания циклов:

```c
#pragma omp parallel for
for (int i = 0; i < n; i++) {
    result[i] = compute(data[i]);
}
```

— Компилятор распределяет итерации цикла по доступным ядрам. OpenMP эффективен для рабочих нагрузок с параллельными данными (одинаковая операция со многими точками данных) и широко используется в научных вычислениях.

- **Параллелизм передачи сообщений**: каждый процесс имеет собственную память. Общение происходит путем отправки и получения сообщений. **MPI** (Интерфейс передачи сообщений) — это стандарт распределенных вычислений между узлами:

```c
MPI_Send(data, count, MPI_FLOAT, dest, tag, MPI_COMM_WORLD);
MPI_Recv(data, count, MPI_FLOAT, src, tag, MPI_COMM_WORLD, &status);
```

— MPI масштабируется до тысяч узлов, поскольку нет общего состояния для синхронизации. Распределенное глубокое обучение (глава 6) использует коллективные операции, такие как `MPI_AllReduce` (кольцевое сокращение всех элементов), для синхронизации градиентов между графическими процессорами.

- **Параллелизм графического процессора** соответствует модели **SIMT** (одна инструкция, несколько потоков): тысячи потоков выполняют одну и ту же инструкцию для разных данных. Это идеально подходит для матричных операций (глава 2), где к каждому элементу применяется одно и то же умножение-сложение. Мы подробно рассмотрим программирование графического процессора в следующей главе.

## Асинхронное и событийно-ориентированное программирование

— Не для любого параллелизма нужны потоки. **Асинхронное** программирование позволяет решать множество задач, связанных с вводом-выводом, в одном потоке с использованием **цикла событий**.

— Цикл событий поддерживает очередь задач. Когда задаче необходимо дождаться ввода-вывода (ответа сети, чтения файла), она регистрирует обратный вызов и передает управление. Цикл событий выбирает следующую готовую задачу. Когда ввод-вывод завершается, обратный вызов ставится в очередь и в конечном итоге выполняется. Во время ожидания ни один поток не блокируется.

- **Сопрограммы** — это функции, которые могут приостанавливать и возобновлять работу. Синтаксис `async/await` (Python, JavaScript, Rust) делает сопрограммы похожими на обычный последовательный код:

```python
async def fetch_data(url):
    response = await http_get(url)  # suspends here, event loop runs other tasks
    return process(response)         # resumes when response arrives
```

- Ключевое слово `await` приостанавливает сопрограмму и возвращает управление циклу событий. Когда ожидаемая операция завершится, сопрограмма продолжит работу с того места, где она остановилась. Это кооперативная многозадачность: сопрограммы добровольно уступают место, в отличие от вытесняющей многозадачности, когда ОС принудительно переключает потоки.

- Асинхронный режим идеально подходит для рабочих нагрузок **связанных с вводом-выводом** со множеством одновременных подключений (веб-серверы, обслуживающие тысячи клиентов). Он не подходит для работы **с привязкой к процессору** (однопоточный цикл обработки событий не может использовать несколько ядер). Для работы с нагрузкой на ЦП используйте потоки или процессы.

- **Глобальная блокировка интерпретатора (GIL)** Python предотвращает настоящий параллелизм с потоками: только один поток может одновременно выполнять байт-код Python. Вот почему Python использует многопроцессорность (отдельные процессы, каждый со своим интерпретатором) для параллелизма ЦП и асинхронность для параллелизма ввода-вывода. GIL удаляется из Python 3.13+ (свободнопоточный Python), что обеспечивает настоящий многопоточный параллелизм.

## Законы масштабирования

- **Закон Амдала** описывает теоретическое ускорение программы при распараллеливании. Если часть программы $p$ является распараллеливаемой, а остальная часть $1 - p$ является последовательной:

$$\text{Speedup}(n) = \frac{1}{(1-p) + \frac{p}{n}}$$

![Amdahl's law: the serial fraction limits maximum speedup — 10% serial means 10x max, no matter how many cores](../images/amdahl_serial_bottleneck.svg)

- где $n$ - количество процессоров. Для $n \to \infty$ максимальное ускорение приближается к $\frac{1}{1-p}$. Если 95% программы выполняется параллельно, максимальное ускорение составляет $\frac{1}{0.05} = 20\times$, независимо от того, сколько ядер вы добавите. Серийная часть является узким местом.- Это имеет серьезные последствия для машинного обучения: если загрузка данных занимает 10% времени обучения и является последовательной, добавление большего количества графических процессоров может ускорить обучение максимум в 10 раз. Узкое место последовательного порта в 10% ограничивает все (вот почему эффективные конвейеры данных и перекрытие вычислений с вводом-выводом имеют значение, глава 6).

- **Закон Густавсона** предлагает более оптимистичную перспективу. Вместо того, чтобы фиксировать размер задачи и добавлять процессоры, он фиксирует общее время и спрашивает, сколько еще работы можно выполнить. Если параллельная часть масштабируется вместе с размером проблемы:

$$\text{Speedup}(n) = 1 - p + p \cdot n$$

- Это линейно в $n$. Аргумент: чем больше процессоров, тем быстрее мы решаем более крупные проблемы, а не одну и ту же проблему. В машинном обучении это соответствует увеличению размера пакета за счет большего количества графических процессоров (слабое масштабирование), а не сохранению фиксированного размера пакета (сильное масштабирование).

## Задачи по кодированию (используйте CoLab или блокнот)

1. Продемонстрируйте состояние гонки. Два потока увеличивают общий счетчик без синхронизации и наблюдают за потерянными обновлениями.
```python
import threading

counter = 0

def increment(n):
    global counter
    for _ in range(n):
        counter += 1  # NOT atomic: read, add, write

threads = [threading.Thread(target=increment, args=(100000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()

print(f"Expected: {4 * 100000}")
print(f"Actual:   {counter}")
print(f"Lost updates: {4 * 100000 - counter}")
```

2. Зафиксируйте состояние гонки с помощью блокировки и измерьте накладные расходы.
```python
import threading
import time

lock = threading.Lock()
counter = 0

def increment_locked(n):
    global counter
    for _ in range(n):
        with lock:
            counter += 1

start = time.time()
threads = [threading.Thread(target=increment_locked, args=(100000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
elapsed = time.time() - start

print(f"Counter: {counter} (correct: {4 * 100000})")
print(f"Time with lock: {elapsed:.3f}s")
```

import jax.numpy as jnp
import matplotlib.pyplot as plt

n_procs = jnp.arange(1, 65)

for p, color in [(0.5, "#e74c3c"), (0.9, "#f39c12"), (0.95, "#27ae60"), (0.99, "#3498db")]:
    speedup = 1 / ((1 - p) + p / n_procs)
    plt.plot(n_procs, speedup, color=color, linewidth=2, label=f"p={p}")
    # Max speedup line
    plt.axhline(1 / (1 - p), color=color, linestyle="--", alpha=0.3)

plt.xlabel("Number of processors")
plt.ylabel("Speedup")
plt.title("Amdahl's Law: Serial Fraction Limits Speedup")
plt.legend()
plt.grid(True)
plt.show()
