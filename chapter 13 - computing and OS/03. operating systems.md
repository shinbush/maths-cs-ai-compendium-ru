# Операционные системы

*Операционная система — это программный уровень между оборудованием и приложениями, управляющий ресурсами, обеспечивающий абстракции и обеспечивающий изоляцию. В этом файле описывается, что делает ОС, процессы, потоки, планирование ЦП, управление памятью, файловые системы и системные вызовы*.

— Компьютер без операционной системы — это как кухня без повара: ингредиенты (оборудование) есть, но ничего не согласовывает, кто пользуется плитой, куда ставить посуду или как не дать двум людям схватить один и тот же нож. **ОС** является этим координатором.

- Для специалистов по машинному обучению концепции ОС объясняют: почему `nvidia-smi` показывает использование памяти графического процессора для каждого процесса, почему обучение завершается с ошибкой «недостаточно памяти», почему `fork()` дублирует ваш процесс Python и почему контейнеры Docker предоставляют изолированные среды.

## Что делает операционная система

- У ОС есть три основные обязанности:

    - **Абстракция**: скройте сложность оборудования за чистыми интерфейсами. Программы читают и записывают «файлы», не зная, является ли базовое хранилище SSD, HDD или сетевым диском. Они выделяют «память», не управляя микросхемами физического ОЗУ. Они работают на «ЦП», не беспокоясь о прерываниях и согласованности кэша.

    - **Управление ресурсами**: несколько программ совместно используют процессор, память, диск и сеть. ОС решает, кто, что, когда и как долго получит. Справедливая и эффективная стратегия распределения обеспечивает отзывчивость системы.

    - **Изоляция и защита**: программы не должны мешать друг другу. Ошибка в вашем веб-браузере не должна привести к сбою ядра. Вредоносная программа не должна читать пароли другой программы. ОС обеспечивает соблюдение границ с помощью аппаратной поддержки (уровни привилегий, виртуальная память).

## Процессы

- **процесс** – это работающая программа. Это фундаментальная единица работы ОС. Каждый процесс имеет:

    - **Код** (инструкции программы, только для чтения).
    - **Данные** (глобальные переменные, распределение кучи).
    - **Стек** (фреймы вызова функций, локальные переменные).
    - **Состояние** (значения регистров, счетчик программ, открытые файлы и т. д.).

- **Блок управления процессом (PCB)** — это структура данных ОС для отслеживания процесса. Он хранит идентификатор процесса (PID), состояние, счетчик программ, содержимое регистров, карты памяти, дескрипторы открытых файлов и приоритет планирования. Когда ОС переключается с одного процесса на другой, она сохраняет состояние текущего процесса на своей плате и загружает состояние следующего процесса. Это **переключатель контекста**.

— Переключение контекста обходится дорого: сохранение и восстановление регистров, очистка кешей и аннулирование записей TLB занимают микросекунды. В системе, выполняющей тысячи процессов, накладные расходы могут быть значительными. Вот почему серверные архитектуры «процесс-запрос» (например, старый Apache) были заменены архитектурами, основанными на потоках или событиях.

- **Создание процесса** в Unix использует `fork()` и `exec()`:

    - `fork()` создает **копию** текущего процесса. Дочерний процесс получает копию памяти, файловых дескрипторов и состояния родительского процесса. Оба процесса продолжают выполняться с одной и той же точки, но `fork()` возвращает 0 в дочернем процессе и PID дочернего процесса в родительском.

    - `exec()` заменяет текущий код процесса новой программой. После `fork()` ребенок обычно вызывает `exec()`, чтобы запустить другую программу.

    — Эта модель fork-then-exec элегантна: создание нового процесса (fork) и загрузка новой программы (exec) — это отдельные операции, которые можно настраивать независимо. Между fork и exec дочерний процесс может перенаправить ввод-вывод, изменить переменные среды или отказаться от привилегий.

- **Состояния процесса**: процесс находится в одном из нескольких состояний:
    - **Выполняется**: в данный момент выполняется на ядре ЦП.
    - **Готов**: ожидание ядра ЦП (работающего, но еще не запланированного).
    - **Заблокировано** (ожидание): невозможно продолжать работу до тех пор, пока не произойдет какое-либо событие (завершение ввода-вывода, получение блокировки, истечение таймера).
    - **Завершено**: выполнение завершено, ожидание, пока родительский элемент получит статус завершения.

## Темы– **поток** — это облегченная исполнительная единица внутри процесса. Все потоки в процессе используют один и тот же код, данные и кучу, но каждый из них имеет собственное состояние стека и регистра.

- Преимущество перед несколькими процессами: потоки совместно используют память, поэтому связь между ними происходит быстро (просто чтение/запись общих переменных). Процессам требуется межпроцессное взаимодействие (каналы, сокеты, сопоставления общей памяти), которое медленнее и сложнее.

- Недостаток: общая память опасна. Два потока, записывающие одну и ту же переменную одновременно, вызывают **состояние гонки** (результат зависит от того, какой поток запускается первым). Это приводит нас к синхронизации, описанной в файле 4.

- **Потоки ядра** управляются планировщиком ОС. Каждый поток независимо распределяется по ядрам ЦП. Создание и переключение потоков ядра включает в себя системные вызовы, накладные расходы которых аналогичны (но меньше) переключению контекста процесса.

- **Пользовательские потоки** (зеленые потоки) управляются библиотекой времени выполнения в пользовательском пространстве, невидимой для ОС. Их дешевле создавать и переключать (не требуется системный вызов), но операция блокировки одним пользовательским потоком блокирует все потоки в процессе (поскольку ОС видит только один поток ядра).

- Современные системы используют **гибридные модели**: многие пользовательские потоки отображаются на меньшее количество потоков ядра (потоки M:N). Горутины Go и процессы Erlang — это потоки пользовательского уровня, запланированные средой выполнения языка в потоках ОС.

- **Пулы потоков** предварительно создают фиксированное количество потоков, ожидающих выполнения задач. Когда задача поступает, она назначается простаивающему потоку. Это позволяет избежать накладных расходов на создание и уничтожение потоков для каждой задачи. Веб-серверы, механизмы баз данных и серверы вывода ML используют пулы потоков.

## Планирование ЦП

- **Планировщик** решает, какой процесс/поток выполняется на каком ядре ЦП в каждый момент времени. Цели: максимизировать загрузку ЦП, минимизировать время ответа (для интерактивных задач), максимизировать пропускную способность (для пакетных задач) и обеспечить справедливость.

- **В порядке очереди (FCFS)**: процессы выполняются в порядке поступления. Просто, но страдает от **эффекта конвоя**: длительный процесс блокирует все более короткие процессы, стоящие за ним.

- **Сначала самое короткое задание (SJF)**: сначала запустите самый короткий процесс. Доказуемо минимизирует среднее время ожидания, но требует заранее знать длину задания (в целом это невозможно). Версия с вытеснением, **Сначала наименьшее оставшееся время (SRTF)**, прерывает выполняющееся задание, если поступает более короткое задание.

- **Раундный алгоритм (RR)**: каждый процесс получает фиксированный **квант времени** (например, 10 мс), затем вытесняется и перемещается в конец очереди. Честный и отзывчивый, но временной интервал имеет значение: слишком маленький означает чрезмерное переключение контекста, слишком большой приводит к FCFS.

- **Приоритетное планирование**: каждый процесс имеет приоритет. Процессы с более высоким приоритетом запускаются первыми. Опасность заключается в **голоде**: процессы с низким приоритетом могут никогда не запуститься, если процессы с высоким приоритетом продолжают поступать. **Старение** решает эту проблему: чем дольше процесс ожидания, тем выше его приоритет.

- **Многоуровневые очереди обратной связи (MLFQ)**: несколько очередей с разными приоритетами и временными квантами. Новые процессы запускаются в очереди с наивысшим приоритетом (короткий такт). Если процесс использует свой полный квант (зависит от процессора), он понижается до очереди с более низким приоритетом (более длинный квант). Интерактивные процессы естественным образом остаются в очередях с высоким приоритетом (они блокируются для ввода-вывода перед использованием своего кванта). Это адаптируется к рабочей нагрузке, не требуя предварительного знания типов работ.

- **Полностью честный планировщик (CFS)**: планировщик Linux. Он поддерживает красно-черное дерево (сбалансированное двоичное дерево поиска) процессов, отсортированных по «виртуальному времени выполнения» — количеству процессорного времени, которое они потребляют. Следующим запускается процесс с наименьшим виртуальным временем выполнения. Это гарантирует, что со временем каждый процесс получит свою справедливую долю. CFS выполняется через $O(\log n)$ в соответствии с решением планирования.

## Управление памятью

- ОС управляет физической оперативной памятью, выделяя ее процессам и освобождая, когда она больше не нужна.- **Пейджинг** (из файла 2) делит виртуальную память на страницы фиксированного размера, а физическую память - на кадры. Таблица страниц сопоставляет страницы с фреймами. Пейджинг устраняет внешнюю фрагментацию (потеря пространства между выделениями), поскольку все страницы имеют одинаковый размер.

- **Подкачка по требованию** загружает страницы в ОЗУ только при первом доступе к ним (а не при запуске процесса). Это экономит память: программа с 1 ГБ кода может использовать только 50 МБ во время обычного запуска. Остальное никогда не загружается.

- Когда ОЗУ заполнено и требуется новая страница, ОС должна **удалить** существующую страницу. Алгоритмы **замены страниц** (LRU, FIFO, часы, из файла 2) решают, какую страницу следует исключить. Хорошая замена сводит к минимуму ошибки страниц; плохая замена приводит к тряске.

- **Сегментация** делит память на сегменты переменного размера (код, данные, стек, куча), каждый из которых имеет свой собственный базовый адрес и длину. Сегменты обеспечивают логическую организацию, а разбиение на страницы обеспечивает физическое управление. Современные системы минимально используют сегментацию (в основном для защиты) и полагаются на подкачку для управления памятью.

- **Куча** – это место, где находится динамически выделяемая память (`malloc`/`free` в C, `new` в Java, неявно в Python). ОС предоставляет процессу большие фрагменты памяти, а **распределитель памяти** (например, `glibc malloc`, `jemalloc`, `tcmalloc`) разделяет эти фрагменты на более мелкие. Конструкция распределителя влияет на производительность: фрагментация приводит к потере пространства, а конкуренция между потоками приводит к потере времени.

## Файловые системы

- **Файловая система** организует данные на постоянном носителе (SSD, HDD) в виде иерархии именованных файлов и каталогов.

- **inode** (индексный узел) хранит метаданные файла: размер, право собственности, разрешения, временные метки и указатели на блоки данных на диске. Имя файла сохраняется в каталоге, который сопоставляет имена с номерами индексных дескрипторов. Такое разделение означает, что файл может иметь несколько имен (**жесткие ссылки**), указывающих на один и тот же индексный дескриптор.

- **FAT** (Таблица размещения файлов): простая файловая система, используемая на USB-накопителях и SD-картах. Таблица сопоставляет каждый кластер (блок) со следующим кластером в файле, образуя связанный список. Простой, но плохо поддерживает разрешения, ведение журнала и большие файлы.

- **ext4**: файловая система Linux по умолчанию. Использует индексные дескрипторы с прямыми, косвенными, двойными и тройными косвенными указателями блоков для обработки файлов любого размера. Поддерживает **экстенты** (непрерывные диапазоны блоков) для повышения эффективности работы с большими файлами. Максимальный размер файла: 16 ТБ, максимальный размер раздела: 1 ЭБ.

- **Журналирование** защищает от повреждения и сбоев. Перед изменением структуры файловой системы изменения записываются в **журнал** (журнал). Если система выходит из строя во время операции, журнал воспроизводится при перезагрузке для завершения или отмены операции. Без ведения журнала сбой во время записи может привести к тому, что файловая система окажется в несогласованном состоянии (блоки данных файла обновятся, а его индексный дескриптор — нет, или наоборот).

- **Файловые системы на основе B-дерева** (Btrfs, ZFS) используют B-деревья (сбалансированные деревья поиска) для организации данных и метаданных, обеспечивая эффективный поиск, копирование при записи снимков и встроенные контрольные суммы для обеспечения целостности данных. Это те же B-деревья, которые используются в индексах баз данных.

## Системные вызовы и режим ядра

- **Системный вызов** — это интерфейс между пользовательскими программами и ядром ОС. Когда программе нужно сделать что-то привилегированное (прочитать файл, выделить память, создать процесс, отправить сетевой пакет), она выполняет системный вызов.

- ЦП работает в двух режимах:
    - **Режим пользователя**: ограничен. Программы могут выполнять свой собственный код и получать доступ к собственной памяти, но не могут напрямую обращаться к оборудованию, памяти других процессов или структурам данных ОС.
    - **Режим ядра**: неограниченно. Ядро ОС имеет доступ ко всему оборудованию и памяти. Системные вызовы — это управляемый шлюз из пользовательского режима в режим ядра.- Когда программа вызывает `read()`, происходит следующее:
    1. Программа помещает аргументы в регистры и запускает **ловушку** (программное прерывание).
    2. ЦП переключается в режим ядра и переходит к обработчику системных вызовов.
    3. Ядро проверяет аргументы, выполняет операцию ввода-вывода и копирует данные в пользовательский буфер.
    4. Ядро переключается обратно в пользовательский режим и возвращает результат.

- Общие системные вызовы: `open`, `read`, `write`, `close` (файлы), `fork`, `exec`, `wait`, `exit` (процессы), `mmap`, `brk` (память), `socket`, `bind`, `listen`, `accept` (сеть).

- **Прерывания** — это аппаратные сигналы, которые заставляют процессор временно остановить выполнение своих действий и запустить обработчик прерываний (в ядре). Нажатие клавиатуры, прибытие сетевого пакета или отсчет таймера — все это генерирует прерывания. Прерывание по таймеру особенно важно: именно оно позволяет ОС вытеснить запущенный процесс и переключиться на другой (вытесняющая многозадачность).

## Основы работы в сети

— Сетевой стек — это подсистема ОС, обеспечивающая связь между машинами. Понимание этого объясняет, как распределенное обучение синхронизирует градиенты, как обслуживание моделей обрабатывает запросы и почему задержка имеет значение.

![TCP/IP stack: application, transport, network, and link layers, each adding headers](../images/tcp_ip_layers.svg)

- **Модель TCP/IP** организует сеть на уровни, каждый из которых представляет собой абстракцию вышележащего уровня:

    - **Уровень связи**: обеспечивает связь по одному физическому каналу (Ethernet, Wi-Fi). Работает с MAC-адресами и кадрами.
    - **Сетевой уровень (IP)**: пакеты маршрутизируются по нескольким сетям от источника к месту назначения. У каждого компьютера есть **IP-адрес** (например, 192.168.1.1 для IPv4 или 128-битный адрес IPv6). Маршрутизаторы пересылают пакеты шаг за шагом в зависимости от IP-адреса назначения.
    - **Транспортный уровень (TCP/UDP)**: обеспечивает сквозную связь между приложениями.
    - **Уровень приложений**: такие протоколы, как HTTP, DNS, gRPC, которые приложения используют напрямую.

- **TCP** (протокол управления передачей) обеспечивает надежную и упорядоченную доставку. Он устанавливает соединение (трехстороннее рукопожатие: SYN, SYN-ACK, ACK), гарантирует, что все данные прибудут в правильном порядке (с использованием порядковых номеров и подтверждений), повторно передает потерянные пакеты и контролирует скорость отправки, чтобы избежать перегрузки сети (**контроль перегрузки**). Платой за это является задержка: рукопожатие добавляет время туда и обратно, а повторные передачи добавляют задержки.

- **UDP** (протокол пользовательских дейтаграмм) обеспечивает ненадежную неупорядоченную доставку. Никакого рукопожатия, никакой повторной передачи, никакой гарантии заказа. Гораздо меньшая задержка, чем TCP. Используется там, где скорость важнее надежности: потоковое видео, онлайн-игры, поиск DNS. В машинном обучении некоторые протоколы градиентной синхронизации используют RDMA на основе UDP для снижения задержки.

- **Сокеты** — это API ОС для сетевого взаимодействия. **Сокет** — это конечная точка, идентифицируемая (IP-адресом, номером порта). Сервер создает сокет, привязывает его к порту (например, 80 для HTTP), прослушивает соединения и принимает их. Клиент создает сокет и подключается к серверу по адресу:порт. Затем данные читаются и записываются через сокет, как файл.

- **DNS** (система доменных имен) преобразует удобочитаемые имена (google.com) в IP-адреса (142.250.80.46). Это распределенная иерархическая база данных: ваша машина запрашивает локальный преобразователь, который запрашивает корневые серверы, которые делегируют полномочия авторитетным серверам для каждого домена.

- **HTTP** (протокол передачи гипертекста) — это веб-протокол запросов и ответов. Клиент отправляет запрос (метод + URL-адрес + заголовки + необязательное тело), ​​а сервер отправляет ответ (код состояния + заголовки + тело). Обслуживание моделей ML (например, TensorFlow Serving, Triton) предоставляет модели как конечные точки HTTP или gRPC.- **Задержка в зависимости от пропускной способности**: задержка — это время, в течение которого один пакет перемещается от источника к месту назначения (определяется физическим расстоянием и сетевыми переходами). Пропускная способность — это скорость передачи данных (сколько байт в секунду). Соединение с высокой пропускной способностью и высокой задержкой (спутниковый Интернет) может передавать большие объемы данных, но доставка каждого байта занимает много времени. Для распределенного обучения **задержка** имеет значение для барьеров синхронизации (все графические процессоры должны ждать самого медленного), а **пропускная способность** важна для передачи больших тензоров градиента (глава 6).

## Виртуализация и контейнеры

- **Виртуализация** позволяет запускать несколько операционных систем на одном физическом компьютере. **Гипервизор** (VMware, KVM, Xen) создает **виртуальные машины (ВМ)**, каждая из которых имеет собственный виртуальный процессор, память, диск и сетевой интерфейс. На каждой виртуальной машине установлена ​​полноценная операционная система (гостевая ОС), которая считает, что у нее есть выделенное оборудование.

- Виртуальные машины обеспечивают надежную изоляцию (сбой одной виртуальной машины не влияет на другие) и гибкость (запуск Linux и Windows на одной машине, миграция виртуальных машин между физическими хостами). Затраты — это накладные расходы: каждая виртуальная машина запускает полное ядро ​​ОС, потребляя память и ЦП для операций ОС, которые избыточны для ОС хоста.

![VMs run separate guest OSes on virtual hardware; containers share the host kernel and are much lighter](../images/container_vs_vm.svg)

- **Контейнеры** (Docker, Podman) представляют собой более легкую альтернативу. Вместо виртуализации всего оборудования контейнеры совместно используют ядро ОС хоста и используют функции ядра для изоляции процессов:

    - **Пространства имен** изолируют то, что может видеть процесс: каждый контейнер получает собственное представление дерева процессов (пространство имен PID), сетевых интерфейсов (пространство имен сети), точек монтирования файловой системы (пространство имен монтирования) и имени хоста (пространство имен UTS). Процесс внутри контейнера не может видеть процессы в других контейнерах.

    - **Cgroups** (группы управления) ограничивают то, что процесс может использовать: время процессора, память, дисковый ввод-вывод, пропускную способность сети. Контейнер не может потреблять больше ресурсов, чем позволяет его контрольная группа, что не позволяет одному контейнеру истощать другие.

– Контейнеры запускаются за миллисекунды (без загрузки ОС), используют минимальные накладные расходы (общее ядро) и определяются **Dockerfile**, в котором указаны базовый образ, зависимости и команды. Это делает их воспроизводимыми: `docker build` везде создает одну и ту же среду.

- Для машинного обучения контейнеры решают проблему «это работает на моей машине». Учебная среда с конкретными версиями CUDA, cuDNN, PyTorch и Python упаковывается в виде образа контейнера. Любой может воспроизвести точную среду на любой машине. Платформы облачного обучения (AWS SageMaker, GCP Vertex AI) выполняют задания обучения в контейнерах.

- **Kubernetes** (K8s) оркестрирует контейнеры в масштабе: он планирует размещение контейнеров в кластере компьютеров, перезапускает отказавшие контейнеры, масштабируется вверх/вниз в зависимости от нагрузки и управляет сетью между контейнерами. Крупномасштабное обслуживание машинного обучения (тысячи реплик моделей, обрабатывающих миллионы запросов) выполняется в Kubernetes.

## Основы безопасности

- ОС обеспечивает безопасность с помощью нескольких механизмов:

- **Разрешения**: каждый файл имеет владельца, группу и биты разрешений (чтение/запись/выполнение для владельца, группы и других). Процесс запускается с идентификатором (UID) пользователя, который его запустил, и может получить доступ только к файлам, которые разрешены битами разрешений. Пользователь **root** (UID 0) обходит все проверки разрешений, поэтому работать с правами root опасно.

- **Разделение привилегий**: процессы выполняются с минимальными необходимыми привилегиями. Веб-серверу не требуется root-доступ; он должен работать как пользователь с ограниченными правами, который может только читать веб-файлы и привязываться к порту 80. Если сервер взломан, доступ злоумышленника ограничен тем, что может делать пользователь с ограниченными правами.

- **Песочница**: ограничивайте действия процесса, выходящие за рамки прав доступа к файлу. **seccomp** (Linux) ограничивает системные вызовы, которые может выполнять процесс. **AppArmor** и **SELinux** определяют политики обязательного контроля доступа. Контейнеры объединяют пространства имен, cgroups и seccomp для многоуровневой изоляции.

- **Рандомизация структуры адресного пространства (ASLR)**: рандомизация ячеек памяти стека, кучи и библиотек при каждом запуске программы. Это усложняет злоумышленникам использование ошибок повреждения памяти (переполнение буфера), поскольку они не могут предсказать, где в памяти будет находиться код или данные.- Безопасность является общесистемной проблемой: цепочка сильна настолько, насколько прочно ее самое слабое звено. Система обслуживания модели нуждается в безопасной сетевой связи (TLS/HTTPS), аутентифицированном доступе к API (ключи API, OAuth), проверке входных данных (предотвращение состязательных входных данных) и изолированном выполнении (контейнеры с минимальными привилегиями).

pid = os.fork()

if pid == 0:
    # Child process
    print(f"Child: my PID is {os.getpid()}, parent PID is {os.getppid()}")

2. Имитировать циклическое планирование. Имея список процессов с периодами пиковой нагрузки, смоделируйте планирование и вычислите среднее время ожидания.
```python
def round_robin(processes, quantum=3):
    """Simulate round-robin scheduling.
    processes: list of (name, burst_time) tuples.
    """
    queue = [(name, burst, 0) for name, burst in processes]  # (name, remaining, wait)
    time = 0
    log = []

    while queue:
        name, remaining, waited = queue.pop(0)
        waited += (time - waited - (processes[[p[0] for p in processes].index(name)][1] - remaining))
        run_time = min(quantum, remaining)
        log.append(f"  t={time:3d}: {name} runs for {run_time} (remaining: {remaining - run_time})")
        time += run_time
        remaining -= run_time

        if remaining > 0:
            queue.append((name, remaining, time))
        else:
            log.append(f"  t={time:3d}: {name} DONE (turnaround: {time})")

    for line in log:
        print(line)

print("Round Robin (quantum=3):")
round_robin([("P1", 10), ("P2", 4), ("P3", 6)], quantum=3)
```

3. Имитируйте замену страниц с помощью LRU. Учитывая последовательность обращений к страницам и фиксированное количество кадров, подсчитайте ошибки страниц.
```python
def lru_page_replacement(pages, n_frames):
    """Simulate LRU page replacement."""
    frames = []
    faults = 0

    for page in pages:
        if page in frames:
            frames.remove(page)
            frames.append(page)  # move to most recently used
            status = "HIT "
        else:
            faults += 1
            if len(frames) >= n_frames:
                evicted = frames.pop(0)  # remove least recently used
                status = f"MISS (evict {evicted})"
            else:
                status = "MISS (cold)"
            frames.append(page)
        print(f"  Page {page}: {status}  frames={frames}")

    print(f"\nTotal faults: {faults}/{len(pages)} ({faults/len(pages):.0%})")

print("LRU with 3 frames:")
lru_page_replacement([1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5], n_frames=3)
```
