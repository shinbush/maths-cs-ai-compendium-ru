# Обслуживание и пакетирование

*Обслуживание LLM тысячам одновременных пользователей требует большего, чем просто загрузка модели и выполнение вывода. В этом файле описаны разделение предварительного заполнения и декодирования, непрерывная пакетная обработка, PagedAttention и vLLM, стратегии планирования, дезагрегированное обслуживание, многомодельное обслуживание и обслуживание LoRA, а также важные показатели *

- Один запрос на вывод LLM прост: введите токены, сгенерируйте выходные токены. Но обслуживание LLM для 10 000 одновременных пользователей с низкой задержкой и высокой пропускной способностью является системной проблемой. Наивный подход (обработка одного запроса за раз) тратит более 90% мощности графического процессора. Интеллектуальная пакетная обработка и планирование могут увеличить пропускную способность в 10–50 раз без добавления оборудования.

## Предварительное заполнение и декодирование: две совершенно разные фазы

- Вывод LLM состоит из двух отдельных фаз с принципиально разными вычислительными характеристиками:

- **Предварительное заполнение** (быстрая обработка): обработка всех входных токенов одновременно. Это одно большое умножение матрицы: $O(\text{prompt\_length} \times d_{\text{model}}^2)$. Приглашение может обрабатываться параллельно (все токены известны). Предварительное заполнение **зависимо от вычислений**: узким местом являются ALU графического процессора.

- **Декодирование** (генерация токенов): генерация одного токена за раз в авторегрессионном режиме. Каждый новый токен требует обслуживания всех предыдущих токенов через KV-кэш. Декодирование **ограничено пропускной способностью памяти**: графический процессор тратит большую часть времени на загрузку весов модели и KV-кэш из памяти, а не на вычисления. На каждом этапе декодирования создается только один токен, но необходимо загрузить всю модель (~ 140 ГБ для модели 70B в FP16).

- Последствия:

| | Предварительное заполнение | Декодировать |
|--|---------|--------|
| Токены обработаны | Все сразу (параллельно) | По одному (последовательно) |
| Узкое место | Вычисление (флопс) | Пропускная способность памяти |
| Арифметическая интенсивность | Высокий | Очень низкий |
| Использование графического процессора | Высокий (50-80%) | Низкий (1-10%) без дозирования |
| Метрика задержки | **Время получения первого токена (TTFT)** | **Время на выходной токен (TPOT)** |

- TTFT имеет значение для пользовательского опыта (как долго до начала потоковой передачи ответа). TPOT определяет воспринимаемую скорость генерации. Пользователи терпят более высокое TTFT (1–5 секунд), но ожидают более быстрого TPOT (30–100 мс на токен для диалоговых приложений).

## Статическая пакетная обработка (простая)

— Простейшая пакетная обработка: собирайте запросы $B$, дополняйте их до одинаковой длины, обрабатывайте как один пакет.

- **Проблема 1**: запросы имеют разную длину запроса и генерируют разное количество выходных токенов. Короткие запросы завершаются раньше, но перед запуском следующего пакета необходимо дождаться самого длинного запроса в пакете. Графический процессор простаивает, генерируя один оставшийся длинный запрос.

- **Проблема 2**: вычисление отходов заполнения. Если самое длинное приглашение содержит 2000 токенов, а самое короткое — 50, пакет дополняется до 2000. Графический процессор обрабатывает 1950 токенов заполнения для короткого запроса — пустая трата.

## Непрерывная пакетная обработка

- **Непрерывная пакетная обработка** (также называемая пакетной обработкой на уровне итерации) решает обе проблемы, работая с детализацией отдельных шагов декодирования, а не целых запросов.

- На каждом этапе декодирования:
    1. Все текущие запросы генерируют один токен параллельно (в пакетном режиме).
    2. Запросы, которые завершаются (генерируют токен EOS), немедленно **удаляются** из пакета.
    3. Новые запросы из очереди немедленно **вставляются** в освободившиеся слоты.

- Размер партии динамически меняется на каждом этапе. Графический процессор никогда не простаивает в ожидании отстающих, и не происходит ненужного заполнения (каждый запрос использует только те слоты, которые ему необходимы).

- **Воздействие**: непрерывная пакетная обработка обычно увеличивает пропускную способность в 2–10 раз по сравнению со статической пакетной обработкой без изменения качества модели или значительного увеличения задержки.

## PagedAttention и vLLM

- KV-кэш создает кошмар для управления памятью. Каждый запрос имеет KV-кэш, который растет с каждым сгенерированным токеном. Разные запросы находятся на разных стадиях (разные размеры кэша). Выделение непрерывной памяти для каждого запроса приводит к пустой трате места (необходимо выделить максимально возможную длину, даже если запрос генерирует всего несколько токенов).

![PagedAttention maps virtual KV-cache pages to non-contiguous physical GPU memory, eliminating fragmentation and enabling on-demand allocation](../images/paged_attention.svg)- **PagedAttention** (Kwon et al., 2023) применяет концепцию виртуальной памяти ОС (глава 13) к KV-кэшу. Кэш разделен на **страницы** фиксированного размера (блоки позиций токенов). Страницы выделяются по требованию и могут быть несмежными в физической памяти графического процессора.

- Преимущества:
    - **Нет фрагментации**: страницы имеют одинаковый размер, поэтому между запросами нет «дыр» впустую потраченной памяти.
    - **Отложенное выделение**: память выделяется только тогда, когда токены фактически генерируются, а не выделяется заранее на максимальную длину.
    - **Копирование при записи**: запросы, имеющие общий префикс (например, системные запросы), используют одни и те же страницы KV-кэша. Только когда запросы расходятся, страницы копируются.

- **vLLM** — это механизм вывода, построенный на основе PagedAttention. Он обеспечивает в 2–4 раза более высокую пропускную способность, чем обслуживание статического распределения (например, вывод генерации текста HuggingFace без внимания к страницам), практически исключая ненужную трату памяти KV-кэша.

## Стратегии планирования

- Когда в ожидании находится несколько запросов, а графический процессор может обработать только ограниченный пакет, **планирование** решает, какие запросы обслуживать:

- **В порядке очереди (FCFS)**: запросы обрабатываются в порядке поступления. Просто, но несправедливо: пользователь, отправивший генерацию токена 10 000, блокирует всех пользователей, стоящих за ним.

- **Сначала самое короткое задание (SJF)**: обработка запроса, который завершится быстрее всего. Минимизирует среднюю задержку, но наказывает длительно выполняющиеся запросы (они могут «зависнуть»). На практике предполагаемая длина вывода неизвестна, поэтому SJF использует эвристику (длина подсказки, история пользователей).

- **Преимущество**: если поступает запрос с высоким приоритетом, приостановить выполняющийся запрос с более низким приоритетом (заменить его KV-кэш на память ЦП или SSD), обслужить запрос с высоким приоритетом, а затем возобновить приостановленный. vLLM поддерживает это.

- **На основе приоритета**: назначайте приоритеты пользователям или типам запросов. Интерактивные запросы в реальном времени имеют более высокий приоритет, чем задания пакетной обработки. В сочетании с вытеснением это обеспечивает SLO с задержкой для высокоприоритетного трафика.

- **Бюджет токенов**: ограничение общего количества токенов в активном пакете. Это предотвращает монополизацию памяти графического процессора несколькими длинными запросами и прекращение новых запросов.

## Дезагрегированное обслуживание

- Предварительное заполнение и декодирование имеют противоположные вычислительные профили. Запуск обоих на одном и том же графическом процессоре означает, что графический процессор поочередно работает с привязкой к вычислениям (предварительное заполнение) и к пропускной способности памяти (декодирование), никогда не используя полностью ни один из ресурсов.

– **Дезагрегированное показ** разделяет их:
    - **Узлы предварительного заполнения**: графические процессоры, оптимизированные для вычислений (высокий уровень FLOPS, возможно, с меньшим объемом памяти). Обработка всех входящих запросов.
    - **Узлы декодирования**: графические процессоры, оптимизированные для пропускной способности памяти (большая емкость KV-кэша, высокая пропускная способность памяти). Обработка всей генерации токенов.

- Узел предварительного заполнения вычисляет начальный KV-кэш и отправляет его на узел декодирования (через NVLink или сеть). Узел декодирования генерирует токены, используя полученный кэш.

- Это архитектура **Mooncake** (Moonshot AI), которая изучается несколькими обслуживающими командами LLM. Преимущество: каждый тип графического процессора соответствует характеристикам рабочей нагрузки, что повышает общее использование.

## Мультимодель и обслуживание LoRA

- В производстве вы часто обслуживаете несколько моделей (разные размеры для разных уровней, разные доработанные варианты под разные задачи).

- **Мультиплексирование моделей**: загружайте несколько моделей на один и тот же графический процессор и направляйте запросы к соответствующей модели. Память графического процессора является общей: графический процессор емкостью 40 ГБ может одновременно содержать модель 13B (26 ГБ) и модель 7B (14 ГБ).

- **Обслуживание LoRA**: вместо развертывания отдельных точно настроенных моделей разверните одну базовую модель с несколькими **адаптерами LoRA** (глава 6). Каждый адаптер добавляет <1% parameters. Requests are routed to the appropriate adapter at inference time.

- **S-LoRA** (Sheng et al., 2023): serves thousands of LoRA adapters from a single base model. Adapters are stored on CPU and paged into GPU memory on demand. The base model's KV-cache and weights are shared; only the small LoRA matrices differ per request.

- **Punica** (Chen et al., 2023): batches requests across different LoRA adapters by using a custom CUDA kernel that applies different LoRA matrices to different requests within the same batch. This avoids the overhead of switching adapters per request.

## Constrained and Guided Generation

- Many applications need the LLM to produce output in a specific format: valid JSON, SQL queries, code in a particular language, or responses that follow a schema. **Constrained generation** guarantees the output conforms to a grammar or schema.

- **Grammar-constrained decoding**: at each decoding step, mask out tokens that would violate the grammar. If the output so far is `{"name": "Alice", "age":` and the grammar requires an integer next, mask all tokens except digits. The LLM's probability distribution is renormalised over the valid tokens.

- **Outlines** (Willard & Louf, 2023): compiles a JSON schema or regular expression into a finite-state machine (FSM). At each decoding step, the FSM determines which tokens are valid continuations. Invalid tokens get probability 0. This guarantees 100% schema compliance with zero retries.

- **SGLang** integrates constrained generation natively: you specify the output structure in Python, and the engine handles the token masking and caching efficiently. This is combined with RadixAttention (prefix caching) so that structured outputs reuse cached prefixes.

- **Why it matters**: without constrained generation, you generate freely and parse the output, retrying on failure. Retry rates of 10-30% are common for complex JSON schemas, wasting compute. Constrained generation eliminates retries entirely.

## Request Routing

- Not every query needs the biggest model. **Request routing** directs queries to different models based on estimated difficulty:

- **Cascading**: try a small model first. If the small model's confidence is below a threshold (e.g., the softmax probability of the top token is < 0.8), escalate to a larger model. Easy queries (80%+ of traffic) are served cheaply by the small model; only hard queries use the expensive model.

- **Learned routing**: train a lightweight classifier (or use the small model's perplexity) to predict which model tier a query needs. Route "What is 2+2?" to a 3B model and "Explain the mathematical foundations of quantum entanglement" to a 70B model.

- **Impact**: if 80% of queries can be handled by a model that costs 10x less, the average cost per query drops by ~70%. This is one of the highest-impact cost optimisations for multi-model deployments.

- **On-device + cloud hybrid routing**: **Cactus** ([github.com/cactus-compute/cactus](https://github.com/cactus-compute/cactus)) implements request routing at the device level. It runs a small model on-device (phone, laptop, wearable) via custom ARM SIMD kernels, and automatically routes to a cloud model when the local model's confidence is low or the query exceeds the device's capability. The application uses an OpenAI-compatible API for both paths — the routing is transparent. This is cascading at the infrastructure level: the first tier is free (on-device), the second tier costs money (cloud API). For applications where most queries are simple (assistant Q&A, autocomplete, transcription), on-device handling covers 70-90% of traffic at zero marginal cost.

## Inference Metrics

- The right metrics depend on the use case:

| Metric | What It Measures | Target (Conversational) | Target (Batch) |
|--------|-----------------|------------------------|-----------------|
| **TTFT** | Time to first token | <1 s | less important |
| **TPOT** | Time per output token | <100 ms | less important |
| **Throughput** | Tokens/second (total) | less important | maximise |
| **p99 Latency** | Worst 1% of requests | <5 s | <30 s |
| **Cost per token** | $/1M tokens | minimise | minimise |
| **SLO compliance** | % of requests meeting latency target | >99% | >95% |

- **Компромисс TTFT и TPOT**: агрессивная пакетная обработка увеличивает пропускную способность (общее количество токенов в секунду), но увеличивает TPOT (каждый токен занимает больше времени, поскольку графический процессор обрабатывает больше запросов). Стратегия планирования должна балансировать пропускную способность (доход) и задержку (пользовательский опыт).- **Стоимость токена** — это окончательный показатель производства. Он сочетает в себе стоимость оборудования (аренда графического процессора), пропускную способность (токены/с) и загрузку. Система, работающая при 50% загрузке графического процессора, стоит в 2 раза дороже за токен, чем система при 100%. Вот почему пакетирование, планирование и PagedAttention имеют такое большое значение — они повышают загрузку.

## Задачи по кодированию (используйте CoLab или блокнот)

1. Смоделируйте непрерывное и статическое пакетирование и измерьте разницу в производительности.
```python
import random
import time

def simulate_static_batching(requests, batch_size=8):
    """Process requests in fixed batches. Wait for all to finish."""
    total_tokens = 0
    total_time = 0

    for i in range(0, len(requests), batch_size):
        batch = requests[i:i + batch_size]
        max_len = max(r['output_len'] for r in batch)
        # All requests in the batch take as long as the longest
        batch_time = max_len * 0.01  # 10ms per token
        total_time += batch_time
        total_tokens += sum(r['output_len'] for r in batch)

    return total_tokens / total_time  # tokens per second

def simulate_continuous_batching(requests, max_batch=8):
    """Process with continuous batching. Remove finished, add new."""
    total_tokens = 0
    total_time = 0
    active = []
    queue = list(requests)

    while active or queue:
        # Fill batch
        while len(active) < max_batch and queue:
            active.append({'remaining': queue.pop(0)['output_len']})

        if not active:
            break

        # One decode step: all active requests generate 1 token
        for req in active:
            req['remaining'] -= 1
        total_tokens += len(active)
        total_time += 0.01  # 10ms per step

        # Remove finished requests
        active = [r for r in active if r['remaining'] > 0]

    return total_tokens / total_time

# Generate requests with varied output lengths
random.seed(42)
requests = [{'output_len': random.randint(10, 500)} for _ in range(100)]

static_tps = simulate_static_batching(requests)
continuous_tps = simulate_continuous_batching(requests)

print(f"Static batching:     {static_tps:.0f} tokens/s")
print(f"Continuous batching: {continuous_tps:.0f} tokens/s")
print(f"Speedup: {continuous_tps / static_tps:.1f}x")
```

def paged_vs_preallocated(n_requests, max_seq_len, avg_seq_len, page_size, kv_per_token_bytes):
    """Compare memory usage: preallocated vs paged KV-cache."""
    # Preallocated: every request gets max_seq_len slots
    preallocated_gb = n_requests * max_seq_len * kv_per_token_bytes / 1e9

    # Paged: allocate only what is used (with page granularity)
    import math
    avg_pages = math.ceil(avg_seq_len / page_size)
    paged_gb = n_requests * avg_pages * page_size * kv_per_token_bytes / 1e9

    waste_preallocated = (max_seq_len - avg_seq_len) / max_seq_len
    waste_paged = (avg_pages * page_size - avg_seq_len) / (avg_pages * page_size)

    print(f"Requests: {n_requests}, Max seq: {max_seq_len}, Avg seq: {avg_seq_len}")
    print(f"  Preallocated: {preallocated_gb:.1f} GB (waste: {waste_preallocated:.0%})")
    print(f"  Paged:        {paged_gb:.1f} GB (waste: {waste_paged:.0%})")
    print(f"  Savings:      {preallocated_gb - paged_gb:.1f} GB ({preallocated_gb/paged_gb:.1f}x)")
    print()

# Llama-70B: ~1.3 KB per token per layer, 80 layers = ~100 KB per token total
