# Периферийный инференс

*Edge Inference запускает модели на пользовательских устройствах (телефонах, ноутбуках, датчиках Интернета вещей) без отправки данных в облако. Этот файл охватывает граничные ограничения, конвейер сжатия модели, среду выполнения на устройстве, стек компилятора, аппаратные цели (NPU, нейронные механизмы), LLM на устройстве, федеративное обучение и оптимизацию задержек*.

- Облачный вывод требует подключения к сети, увеличивает задержку (50–200 мс туда и обратно), требует денег за запрос и отправляет пользовательские данные на сторонние серверы. **Периферийный вывод** исключает все четыре: модель работает локально, реагирует мгновенно, ничего не требует за вывод и обеспечивает конфиденциальность данных.

- Компромисс: периферийные устройства имеют в 100–1000 раз меньше вычислительных ресурсов и памяти, чем графические процессоры центров обработки данных. Чтобы модели работали в рамках этих ограничений, требуется агрессивная оптимизация на каждом уровне.

- **Cactus** ([github.com/cactus-compute/cactus](https://github.com/cactus-compute/cactus)) — это механизм искусственного интеллекта с малой задержкой, специально созданный для мобильных и носимых устройств. Он демонстрирует многие методы, описанные в этом файле, в действии: специальные ядра ARM SIMD для внимания и матричных операций (глава 16), квантование KV-кэша (глава 17, файл 01), фрагментированное предварительное заполнение, вывод с ускорением NPU на чипах Apple и Qualcomm, отображение памяти с нулевым копированием для десятикратного снижения использования оперативной памяти и автоматический переход в облако, когда вычислений на устройстве недостаточно. Cactus поддерживает мультимодальный вывод (LLM, зрение, речь) в iOS, Android, macOS и встроенном Linux с помощью SDK для Swift, Kotlin, Python, Flutter, React Native и Rust. Его тесты показывают скорость декодирования 100 токенов/с на M4 Pro и 48 токенов/с на iPhone 17 Pro для модели 1.2B в INT4, что является конкретным примером того, как выглядит оптимизированный вывод границ.

## Конвейер сжатия модели

- Для периферийного развертывания сжатие — это не отдельный метод, а **конвейер** дополнительных методов, применяемых последовательно:

```
Full model (FP32, 70B params)
    ↓ Knowledge distillation → smaller model (7B params)
    ↓ Structured pruning → remove redundant heads/layers (4B effective)
    ↓ Quantisation (INT4) → 4x smaller (2 GB)
    ↓ Compiler optimisation → fused kernels, optimised memory layout
    ↓ Runtime → on-device execution
```

- Каждый шаг уменьшает размер и задержку. Порядок имеет значение: сначала дистиллировать (уменьшить архитектуру), затем сократить (удалить структуру), затем квантовать (уменьшить точность), затем скомпилировать (оптимизировать для целевого оборудования). Дистилляция после квантования попытается сжать модель, которая уже имеет потери.

## Среды выполнения на устройстве

- **Среда выполнения** загружает модель, выделяет память и выполняет логический вывод на целевом оборудовании. Каждая платформа имеет свою предпочтительную среду выполнения:

- **ONNX Runtime**: кроссплатформенность (Windows, Linux, macOS, iOS, Android). Поддерживает ЦП, графический процессор (CUDA, DirectML, CoreML, NNAPI) и множество серверных ускорителей. Самый портативный вариант. Модели экспортируются в формат ONNX из PyTorch/TensorFlow.

- **TensorFlow Lite (TFLite)**: передовая среда выполнения Google. Оптимизирован для процессоров ARM и NPU Android. Маленький бинарник (~1 МБ). Поддерживает INT8 и float16. Стандарт для развертывания Android.

- **Core ML**: среда выполнения Apple для iOS/macOS. Автоматически использует Neural Engine, GPU или CPU в зависимости от характеристик модели. Модели конвертируются из PyTorch/TensorFlow с помощью `coremltools`. Тесная интеграция с оборудованием Apple (унифицированная память, Neural Engine).

- **ExecuTorch**: новая среда выполнения Meta для PyTorch на устройстве. Предназначен для развертывания на периферии с предварительной компиляцией и делегированием на уровне оператора аппаратным ускорителям. Преемник PyTorch Mobile.

- **TensorRT**: среда выполнения NVIDIA для оптимизации вывода графического процессора (глава 15). Объединяет слои, выбирает оптимальные ядра и автоматически выполняет квантование. В 2–5 раз быстрее, чем в режиме PyTorch на графических процессорах NVIDIA.- **llama.cpp**: однофайловый механизм вывода C++ для LLM. Поддерживает квантование GGUF (Q4, Q5, Q8), CPU (AVX/NEON), Metal (Apple GPU), CUDA и Vulkan. Идеальное решение для запуска LLM на потребительском оборудовании.

## Стек компилятора

- Между моделью высокого уровня (граф PyTorch) и оборудованием (инструкции NPU) находится **стек компилятора**, который оптимизирует модель для конкретной цели:

```
PyTorch model
    ↓ Export (torch.export, ONNX, TorchScript)
Graph IR (intermediate representation)
    ↓ Graph optimisations
        - Constant folding (compute constant expressions at compile time)
        - Dead code elimination (remove unused operations)
        - Operator fusion (conv + bn + relu → single fused op)
        - Layout transformation (NCHW → NHWC for ARM, channels-last)
    ↓ Lowering
Hardware-specific IR
    ↓ Backend optimisations
        - Tiling and loop ordering (cache-friendly access patterns)
        - Vectorisation (SIMD, chapter 16)
        - Memory planning (reuse buffers to minimise peak memory)
        - Kernel selection (choose the best implementation per op)
    ↓ Code generation
Machine code / NPU instructions
```

- **Слияние операторов** — наиболее эффективная оптимизация. Блок преобразователя имеет около 20 операций (matmul, add, Layernorm, Softmax и т. д.). Без слияния каждый записывает свои выходные данные в память, а следующий считывает их обратно. При слиянии несколько операций объединяются в одно ядро, которое хранит данные в регистрах/кеше. Это может быть в 2–5 раз быстрее (глава 16, модель с линией крыши).

- **Планирование памяти**: компилятор анализирует граф модели, чтобы определить, какие тензоры перекрываются в течение времени жизни и могут использовать один и тот же буфер памяти. Модели со 100 промежуточными тензорами может потребоваться память только для 10, поскольку большинство из них потребляется и освобождается до того, как будут созданы другие. Это критично на устройствах с ограниченной оперативной памятью.

## Аппаратные цели

### Мобильные графические процессоры

- **Qualcomm Adreno** (Android): поддерживает вычисления OpenCL, Vulkan (глава 16) и собственную технологию Qualcomm SNPE (Snapdragon Neural Processing Engine). Графические процессоры Adreno имеют 256–1024 ALU с поддержкой FP16 и INT8.

- **ARM Mali** (Android): поддерживает OpenCL и Vulkan. Графические процессоры Mali используют тайловую архитектуру (отличную от настольных графических процессоров), которая влияет на оптимальные схемы доступа к памяти.

- **Apple GPU** (iOS/macOS): доступ через Metal (API Apple GPU). Унифицированная архитектура памяти означает отсутствие затрат на копирование CPU↔GPU. Шейдеры Metal Performance (MPS) предоставляют оптимизированные примитивы машинного обучения.

### Нейронные процессоры (NPU)

— NPU — это ускорители с фиксированными функциями, разработанные специально для вывода ML. Они гораздо более энергоэффективны, чем графические процессоры, для стандартных операций машинного обучения (matmul, conv, активации).

- **Apple Neural Engine**: 16 ядер, ~38 TOPS (INT8). Доступ через Core ML. Отлично подходит для моделей машинного зрения и распространения на устройствах. Невозможно запустить произвольный код — только операции, поддерживаемые Core ML.

- **NPU Qualcomm Hexagon**: интегрирован в процессоры Snapdragon SoC. Поддерживает вывод INT8 и INT4. Доступ осуществляется через SNPE или ONNX Runtime с серверной частью QNN. Включает такие встроенные в устройство функции, как размытие фона, распознавание речи и перевод в реальном времени.

- **Google Edge TPU**: небольшая версия облачного TPU с низким энергопотреблением. 4 ТОПС, 2Вт. Используется в устройствах Coral для вывода на устройстве. Поддерживает только квантованные модели TFLite INT8.

- **Шаблон делегирования**: среда выполнения разделяет граф модели между NPU (для поддерживаемых операций) и ЦП (для неподдерживаемых операций). Максимизация доли, выполняемой на NPU, является ключом к производительности и энергоэффективности.

## LLM на устройстве

- Запуск LLM на телефонах и ноутбуках стал возможным благодаря небольшим моделям и агрессивному квантованию:

| Модель | Параметры | Квантованный размер | Целевое устройство | Производительность |
|-------|--------|---------------|---------------|-------------|
| Фи-3 Мини | 3,8Б | ~2 ГБ (4 квартал) | Телефон/ноутбук | ~15 токенов/с на iPhone 15 |
| Джемма 2Б | 2Б | ~1,5 ГБ (четвертый квартал) | Телефон | ~20 токенов/с на Pixel 8 |
| Лама 3.2 1Б | 1Б | ~700 МБ (4 квартал) | Телефон | ~30 токенов/с |
| Лама 3.2 3Б | 3Б | ~2 ГБ (4 квартал) | Телефон/ноутбук | ~15 токенов/с |
| Лама 3.1 8Б | 8Б | ~4,5 ГБ (четвертый квартал) | Ноутбук | ~20 токенов/с на M2 |

- **Задачи**:
    - **Память**: у модели 3B Q4 умещается 2 ГБ, но КВ-кэш при длительных разговорах прибавляет существенно. Длина контекста обычно ограничивается 2–4 КБ токенов на телефонах.
    - **Тепловое регулирование**: постоянный вывод нагревает телефон. После 30 секунд непрерывной генерации SoC снижает тактовую частоту, чтобы предотвратить перегрев, снижая производительность на 30–50%.
    - **Батарея**: работа модели 3B со скоростью 15 токенов в секунду потребляет ~3–5 Вт. 30-минутный разговор разряжает примерно 5% батареи обычного телефона. Приемлемо для эпизодического использования, проблематично для постоянно включенных приложений.

- **llama.cpp** — это стандарт для LLM на устройстве. Он работает на процессоре (AVX2, NEON, I8MM), графическом процессоре Apple (Metal), графическом процессоре NVIDIA (CUDA), графическом процессоре AMD (ROCm/Vulkan) и даже на телефонах (через Termux на Android).

## Федеративное обучение- **Федеративное обучение** позволяет обучать модели на многих устройствах без централизации данных. Каждое устройство обучается на своих локальных данных, вычисляет обновление градиента и отправляет только обновление (а не данные) на центральный сервер, который объединяет обновления.

- **Алгоритм** (FedAvg):
    1. Сервер отправляет текущую модель на выбранные устройства $K$.
    2. Каждое устройство выполняет точную настройку модели на основе своих локальных данных за несколько шагов.
    3. Каждое устройство отправляет свою обновленную модель (или разницу) обратно на сервер.
    4. Сервер усредняет обновления: $W_{\text{new}} = \frac{1}{K} \sum_{k=1}^{K} W_k$.
    5. Повторите.

- **Конфиденциальность**: необработанные данные никогда не покидают устройство. Сервер видит только агрегированные обновления модели. **Дифференциальная конфиденциальность** добавляет к обновлениям шум, поэтому отдельные точки данных невозможно реконструировать на основе градиента.

- **Эффективность связи**: обновления модели большие (того же размера, что и модель). Методы сжатия уменьшают эту проблему: **квантование градиента** (отправка градиентов INT8 вместо FP32), **разрежение** (отправка только самых больших градиентов) и **накопление градиента** (выполнение большего количества локальных шагов, отправка реже).

- **Приложения**: подсказки клавиатуры Google (Gboard), распознавание голоса Apple, мониторинг состояния здоровья (обработка конфиденциальных данных о состоянии здоровья без их централизации).

## Оптимизация задержки

- Помимо сжатия, несколько методов уменьшают задержку сквозного вывода:

- **Ранний выход**: добавьте заголовки классификации на промежуточных слоях. Если модель уверена на уровне 6 (из 24), верните прогноз без запуска слоев 7–24. Легкие входы завершаются раньше, жесткие входы используют полную модель. Средняя задержка значительно снижается для задач с сочетанием простых и сложных входных данных.

- **Разделение модели**: разделите модель между NPU (эффективно для matmul), графическим процессором (эффективно для нерегулярных операций) и ЦП (выполняет все остальное). Компилятор решает, какие операции и куда выполнять, на основе профилирования.

- **Кэширование**: для приложений с повторяющимися запросами (автозаполнение, завершение кода) кэшируйте последние вычисления. Если пользователь вводит «Как мне сделать», а модель недавно сгенерировала завершения для «Как мне сделать», кэшированный KV-кэш можно использовать повторно, полностью пропуская этап предварительного заполнения.

- **Спекулятивная предварительная выборка**: предскажите, что пользователь сделает дальше, и начните делать выводы до того, как он спросит. Приложение чата может начать генерировать ответ на вероятный дополнительный вопрос, пока пользователь читает текущий ответ.

```python
def compression_pipeline(original_params_M, original_bits=32):
    size_mb = original_params_M * 1e6 * original_bits / 8 / 1e6

    print(f"Original: {original_params_M}M params, {original_bits}-bit → {size_mb:.0f} MB")

    # Step 1: Knowledge distillation (reduce params)
    distilled_params = original_params_M * 0.15  # 70B → ~10B equivalent
    size_mb = distilled_params * 1e6 * original_bits / 8 / 1e6
    print(f"After distillation ({distilled_params:.0f}M params): {size_mb:.0f} MB")

    # Step 2: Structured pruning (remove 30% of remaining)
    pruned_params = distilled_params * 0.7
    size_mb = pruned_params * 1e6 * original_bits / 8 / 1e6
    print(f"After pruning ({pruned_params:.0f}M params): {size_mb:.0f} MB")

    # Step 3: INT4 quantisation
    size_mb = pruned_params * 1e6 * 4 / 8 / 1e6
    print(f"After INT4 quantisation: {size_mb:.0f} MB")

    print(f"Total compression: {original_params_M * 1e6 * original_bits / 8 / 1e6 / size_mb:.0f}x")

print("=== Starting from 70B model ===")
compression_pipeline(70000)

print("\n=== Starting from 7B model ===")
compression_pipeline(7000)
```
